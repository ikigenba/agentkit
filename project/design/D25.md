# Decision 25 — OpenAI credentials: API key and ChatGPT subscription

**Decision.** The `openai` package's closed credential set (D5) has two members — the only package with more than one. The credential type selects the auth mechanism **and the transport it drags along** (endpoint, headers, body constraints): mechanism is hidden inside the provider; the pick is explicit, structural, and compile-time. The refresh machinery lives in an **opt-in subpackage `openai/subscription`** so consumers that never use it never import disk or OAuth code; the `TokenSource` seam it feeds is declared in `openai` proper (the credential cannot depend on the opt-in package — dependency points inward). **The package contains no login flow**: obtaining the initial credential is the consumer's job, done outside AgentKit with a generic OAuth login tool whose stdout — the token endpoint's response, verbatim — is saved as the credential file.

```go
// package openai

type Credential interface{ isCredential() } // closed: exactly two members
type APIKey string                          // platform API, metered
func Subscription(ts TokenSource) Credential // ChatGPT subscription, flat-rate

// TokenSource supplies the living bearer for subscription auth. Implemented by
// subscription.Store; any implementation works (the seam is what's contractual).
type TokenSource interface {
    Token(ctx context.Context) (bearer, accountID string, err error)
}

func New(cred Credential, opts ...Option) *Provider // one wire: Responses (D5)
```

| baked into the handle | `APIKey` | `Subscription` |
|---|---|---|
| endpoint | `api.openai.com/v1/responses` | `chatgpt.com/backend-api/codex/responses` |
| auth | static `Authorization: Bearer` | per-request bearer from `TokenSource` + `chatgpt-account-id` + `originator: codex_cli_rs` + `OpenAI-Beta: responses=experimental` |
| body constraints | `store:false`, `instructions`, encrypted-reasoning include (already fixed adapter behavior, D9) | identical — the existing adapter already satisfies the backend's requirements |
| model set | vendor judges (free-flow, D5) | backend gates to the subscription's models; rejection is the vendor's loud error |
| cost basis | actual API rates | **notional API-rate-equivalent** (research §15.4) — same D16 resolution over the same supplied rates, no flag, documented here |
| `Name()` / `Error.Provider` / log label | `openai.apikey` | `openai.subscription` |

```go
// package openai/subscription — opt-in: disk + OAuth-refresh machinery, never
// imported by the core provider path. No login flow lives here.

// Load opens the credential file at exactly the path the consumer names — no
// path discovery, no env reading (product: no ambient credential sourcing).
// The file is the raw RFC 6749 token-endpoint response, verbatim (research
// §15.1): top-level access_token, refresh_token, id_token; other standard
// fields ignored. The account id is derived at load from the
// chatgpt_account_id value under the "https://api.openai.com/auth" JWT claim —
// id_token first, access_token as fallback. A file missing access_token, or
// whose JWTs both lack the claim, fails loudly with an error naming what is
// missing; no partial store is returned.
func Load(path string) (*Store, error)

// Store implements openai.TokenSource over the credential file: it returns
// the current access token and the load-derived account id, refreshing
// proactively when the JWT exp is near (and reactively on 401 via the
// provider's retry of an auth-expired category). Refresh rewrites the file
// atomically at mode 0600 in the same raw token-response shape, carrying
// forward the prior refresh_token and id_token when the refresh response
// omits them — so the file always remains re-loadable and the account id
// re-derivable. Single-flight so concurrent requests do not race the file.
// Token values are never logged.
func (s *Store) Token(ctx context.Context) (bearer, accountID string, err error)
```

Settled choices:
- **One provider, one wire, two credentials.** The subscription path speaks the same Responses shape the adapter already implements — `store:false`, mandatory `instructions` (System→instructions), `include:["reasoning.encrypted_content"]` are the D9 fixed behaviors, which is precisely why this is an auth+transport variant, not a second adapter. The transport differences (host/path, extra headers, bearer source) key off the credential type internally.
- **The forced pick is structural.** `APIKey` and `Subscription` take different Go types; there is no mode string, no auto-detect, no fallback (openai-auth.md's settled rule, hardened from env-var vocabulary into the type system by D5).
- **The credential file is the token response, verbatim.** One supported shape: whatever the token endpoint said, saved as-is (the standalone `oauth-login` CLI's stdout contract). The codex CLI's wrapper format (`tokens.*`, `last_refresh`, plain `account_id` field) is not read — the real token response carries no top-level `account_id` (research §15.1), so the previous expectation of one made every real login fail; compatibility with the codex file bought only refresh-lineage contention and is dropped.
- **Account id from the JWT claim.** Derived once at `Load` from `chatgpt_account_id` under the `https://api.openai.com/auth` claim, `id_token` first with `access_token` fallback — the only place the value actually exists. Claim decoding is payload-only (no signature verification; the value is an identifier, not a trust decision — same posture as the existing `exp` peek).
- **Refresh keeps the file self-sufficient.** Refresh responses can omit `id_token` and the account claim (research §15.3), so the rewrite carries the prior `refresh_token`/`id_token` forward when absent; the in-memory account id derived at load stays authoritative for the store's lifetime.
- **No login in the library, and no terminal IO.** Login is a separate program's whole job; AgentKit's surface starts at `Load`. Nothing in the package touches network endpoints other than the token-refresh endpoint, and nothing reads or writes a terminal.
- **Mechanism in agentkit, policy in the consumer.** `subscription.Load(path)` takes an explicit path — resolving *which* path is consumer policy, as is telling the user how to produce the file (e.g. printing an `oauth-login` invocation). The helper reads and maintains exactly the file it is handed: the product's no-ambient-credentials rule holds with the one documented, opt-in exception.
- **Independent lineages.** Refresh rotates a shared refresh-token lineage (research §15.3): the file AgentKit refreshes should be one produced by the consumer's own login, not a copy shared with another live tool. Documented; the live test discipline below observes it.
- **Cost: notional, undistinguished, documented.** Subscription turns resolve cost exactly like API-key turns (D16); the figure is API-rate-equivalent, not spend. No basis flag (operator decision); this table and the package docs are the statement.
- **Labels carry the mode.** `Name()` returns `openai.apikey` / `openai.subscription` — errors, D15 log records, and consumer displays distinguish the modes, since their cost semantics differ.

**Rejected.**
- *`NewCodex` / vendor-codename constructors* — names the vendor's tool, not the thing; operator-rejected.
- *Auth-qualified constructor names (`NewAPIKeyProvider`/`NewSubscriptionProvider`)* — rejected in D5: name = wire × auth explodes; the credential is a typed parameter.
- *A separate `codex`/second provider package* — same models, same wire shape, same vendor; two packages would fork the adapter to vary auth.
- *Auto-detect (key present ? env ? file exists ?)* — silent fallback between billing modes is exactly the surprise the explicit pick exists to prevent.
- *`OPENAI_AUTH_MODE` env resolution inside agentkit* — agentkit never reads env; that resolution is consumer policy (openai-auth.md's catalog `Resolve` sketch lives in the consumer).
- *Keeping the in-library login flow (`BeginLogin`/`Flow`/`Complete`)* — the flow duplicated what a generic OAuth login tool does better (a served callback, a real browser success page), and its parsing of the token response was wrong against the real endpoint. Login is one program's whole job; splitting it across a library seam produced a worse experience at both ends. Deleted outright, no deprecation shim.
- *Accepting both file shapes (codex wrapper + raw response)* — two shapes means silent divergence in what refresh writes back and doubles every load/rewrite test for a compatibility its own doc warned against using.
- *Trusting a top-level `account_id` field* — the previous design; the real token response has no such field (research §15.1), and the codex file that does is no longer read.

**Verification.**
- R-DG9Z-8KYU — a `Send` through `openai.New(openai.Subscription(ts))` (fake `TokenSource`, `httptest` backend) posts to the codex backend path with `Authorization: Bearer <ts-bearer>`, `chatgpt-account-id: <ts-account>`, `originator: codex_cli_rs`, and `OpenAI-Beta: responses=experimental` headers, body carrying `store:false`, non-empty `instructions`, and the encrypted-reasoning include — while `openai.New(openai.APIKey(k))` continues to post to the platform path with none of the subscription headers.
- R-PV6N-URM6 — `Load` on a file holding a raw token-endpoint response (top-level `access_token`/`refresh_token`/`id_token`, no `account_id` field anywhere) succeeds, and `Token` returns the account id carried as `chatgpt_account_id` under the `https://api.openai.com/auth` claim of the `id_token`; with the claim absent from the `id_token` but present in the `access_token`, the access-token value is returned instead — proving the id_token-first, access-token-fallback order.
- R-PWEK-8JCV — `Load` fails loudly, returning no store: on a file with no top-level `access_token` (including a codex-wrapper-shaped file, whose tokens sit nested under `tokens`), with an error naming `access_token`; and on a file whose `id_token` and `access_token` both lack the `chatgpt_account_id` claim, with an error naming the missing account claim — two distinct messages.
- R-DHHV-MCPJ — a `Store` whose access token is expired refreshes at the token endpoint (fake OAuth server), retries carry the new bearer, the rotated tokens are written back atomically with mode `0600`, and N concurrent `Token` calls produce exactly one refresh request (single-flight, asserted on the fake server's request count).
- R-PXMG-MB3K — after a refresh whose response omits `refresh_token` and `id_token`, the rewritten file is still the raw token-response shape and carries the prior `refresh_token` and `id_token` forward, and a fresh `Load` of that rewritten file succeeds and re-derives the same account id; after a refresh whose response *does* rotate them, the rewritten file carries the new values.
- R-DL5K-RNXM — `Name()` returns `openai.apikey` for an `APIKey`-built handle and `openai.subscription` for a `Subscription`-built one, and a provider error from each carries that label in `Error.Provider`.
- R-DJXO-DW6X — **live** (gated on the presence of a local raw-token-response credential file produced by a real `oauth-login` run; skips cleanly otherwise): `subscription.Load` + `Token` yields a bearer and account id the real ChatGPT backend accepts on one completed round trip (a short real `Send` returning an assembled non-error message) — read/use only, no refresh forced against a shared-lineage file — proving the endpoint/header/body contract against the real service.
