# Decision 26 — The advisory model catalog: `agentkit/catalog`

**Decision.** All model knowledge evicted from the provider layer (D5) lives in **one advisory data package, `agentkit/catalog`**: maintained reference data about known models — chat and embedding — plus lookup helpers and typed option builders. It is **consumer-facing only**: nothing in root `agentkit` or any provider package imports it, and nothing in the request path consults it. Its absence for a model restricts nothing (free-flow); its presence makes the common path effortless.

The catalog's unit of knowledge is the **offering** — one model as served by one provider. A model is keyed by name and carries an **ordered list** of the offerings that can serve it: `Offerings[0]` is the default, and the rest are the valid alternatives. Terms that differ by route — rates, reasoning vocabulary, context size, provider options — live on the offering, because they are facts about a *(model, provider)* pair and not about a model.

**The catalog's purpose is that what gets sent works as intended, without surprise.** A cataloged offering is a complete, closed statement of that route's valid options: every value it lists is documented by the serving provider and confirmed to work, and anything it does not list is not a valid way to use that route — regardless of what a permissive gateway happens to tolerate. The consumer never guesses and is never handed a partial answer; the only honest degradations are *route not listed* and *model not cataloged*, both of which pass through untouched.

```go
// package catalog

// Entry is everything the catalog knows about one model, keyed by its model
// name. Model names are assumed globally unique.
type Entry struct {
    Model     string     // the key: "claude-opus-4-8", "glm-5.2", "text-embedding-3-small", …
    Vendor    VendorID   // who built the model — not necessarily anyone who serves it
    Offerings []Offering // ordered by preference; [0] is the default. Never empty.
    Embedding *EmbeddingInfo // embedding entries: rates + capabilities (nil for chat entries)
}

// Offering is one model as served by one provider, with that route's own terms.
// Every shipped chat offering is COMPLETE: non-nil Pricing, non-nil Reasoning,
// Context > 0 (the completeness invariant). nil remains the honest authoring
// zero, rejected by the shipped-data tests.
type Offering struct {
    Provider  agentkit.ProviderID // always a provider package, never a credential mode (D9)
    WireName  string              // "" = derive by the provider's naming rule; set = send verbatim
    Pricing   *agentkit.Pricing   // this route's rates — for Conversation.Pricing
    Reasoning *ReasoningSpec      // this route's reasoning vocabulary + default
    Context   int64               // context-window tokens (advisory display/budgeting)
    Options   json.RawMessage     // default ProviderOptions fragment, when one is advisable
}

// VendorID names who built the model. Its values are spelled exactly as
// OpenRouter spells its vendor namespaces, so the OpenRouter wire name is a
// pure join with no mapping table (see "the wire name is derived").
type VendorID string
const (
    VendorAnthropic VendorID = "anthropic"
    VendorOpenAI    VendorID = "openai"
    VendorGoogle    VendorID = "google"
    VendorZAI       VendorID = "z-ai"
    VendorXAI       VendorID = "x-ai"
    VendorDeepSeek  VendorID = "deepseek"
    VendorMoonshot  VendorID = "moonshotai"
)
```

```go
// ReasoningSpec describes one offering's reasoning vocabulary — the data
// that lets a consumer render, validate, and default reasoning up front
// (D6: validation is advisory, never in the request path). It answers three
// independent questions, and keeps them in three separate places: what values
// may be sent (Levels / Min,Max / Sentinels), which explicit switches the model
// accepts (CanEnable, CanDisable), and what the provider does when nothing is
// sent (Default).
type ReasoningSpec struct {
    Term       string           // "effort" | "thinking level" | "thinking budget" | "thinking"
    Kind       ReasoningKind    // Enum | Range | Toggle
    Levels     []string         // Kind==Enum
    Min, Max   int              // Kind==Range
    Sentinels  []Sentinel       // Range magic values (0=off, -1=dynamic)
    CanEnable  bool             // an explicit on-form exists and the model accepts it (Kind==Toggle only)
    CanDisable bool             // an explicit off-form exists and the model accepts it
    Default    ReasoningDefault // what the provider does on an unset value
}
type ReasoningKind int
const ( ReasoningEnum ReasoningKind = iota; ReasoningRange; ReasoningToggle )
type Sentinel struct{ Value int; Meaning string }

// ReasoningDefault answers "what happens if I send nothing?" — deliberately a
// different type from agentkit.ReasoningValue, which answers "what may I send?".
// Not every provider default is expressible as a value the caller could have
// sent, so typing the default as a ReasoningValue forces a false claim.
type ReasoningDefault struct {
    Mode  ReasoningDefaultMode
    Value agentkit.ReasoningValue // set only when Mode == DefaultFixed
}
type ReasoningDefaultMode int
const (
    DefaultUnaudited ReasoningDefaultMode = iota // zero value: authoring-only; never shipped
    DefaultOff                                   // does not reason unless asked
    DefaultFixed                                 // equivalent to the caller sending Value
    DefaultDynamic                               // provider chooses per request; not caller-controllable
)

// EmbeddingInfo carries an embedding model's rates and capabilities.
type EmbeddingInfo struct {
    Pricing         agentkit.EmbeddingPricing
    NativeDimension int
    MinDimension    int // inclusive producible lower bound
    MaxDimension    int // == NativeDimension
    MaxInputTokens  int // advisory; the provider is the enforcer (D19)
}
```

```go
// Lookup returns the entry for a model name; ok=false for an uncataloged name
// (which remains fully runnable — the caller just gets no conveniences).
func Lookup(model string) (Entry, bool)

// Offerings returns the ordered offerings for a model — [0] the default, the
// rest the valid alternatives — each already carrying that route's rates,
// reasoning vocabulary, and context size. One call answers "where can this
// model go, and on what terms." Nil for an uncataloged model.
func Offerings(model string) []Offering

// Offer returns one model's offering for a named provider, for callers that
// already hold a provider name from elsewhere (a -provider flag, a running
// handle's Identity). Same data the list carries.
func Offer(model string, provider agentkit.ProviderID) (Offering, bool)

// WireModel reports the id a provider is sent on the wire for this entry: the
// matched offering's WireName when set, the provider's naming rule otherwise.
func (e Entry) WireModel(provider agentkit.ProviderID) string

// Resolve answers the two-axis query (a consumer's -provider/-model pair)
// without ever rejecting free-form input. Coverage states how much the catalog
// knows; no value of it blocks a call.
func Resolve(provider agentkit.ProviderID, model string) Resolution

type Resolution struct {
    Vendor    VendorID
    Provider  agentkit.ProviderID
    WireModel string
    Offering  Offering // zero unless Coverage == Curated
    Coverage  Coverage
}

type Coverage int
const (
    Curated  Coverage = iota // an offering matched; terms are whatever it carries
    Passthru                 // a provider was named that has no offering; model sent verbatim
    Unrouted                 // no provider named and no entry; the catalog has no default to give
)

// ListCurated enumerates every entry carrying an offering for a provider —
// catalog rendering for pickers/--help. It reports what the catalog covers,
// never what the provider can serve.
func ListCurated(provider agentkit.ProviderID) []Entry

// Check validates a ReasoningValue against one offering's spec — advisory
// pre-flight for consumers that want errors before spending a round trip. The
// provider argument is required because two offerings of one model may carry
// different vocabularies. ok=false: no offering, nothing to check against.
func Check(model string, provider agentkit.ProviderID, v agentkit.ReasoningValue) (accepted bool, spec *ReasoningSpec, ok bool)
```

```go
// package catalog/openrouterx — typed builder over the ProviderOptions escape
// hatch (D9/D24): convenience, never a gate; unknown future knobs are written
// raw alongside it.

type Routing struct {
    Order          []string
    Only, Ignore   []string
    Sort           string   // "price" | "throughput" | "latency"
    MaxPrice       *MaxPrice
    Quantizations  []string
    ZDR            bool
    AllowFallbacks *bool
}
func (r Routing) ProviderOptions() json.RawMessage // emits {"provider":{...}}
```

**Every shipped offering is complete — there is no unaudited tier.** A shipped chat offering carries a non-nil `Pricing`, a non-nil `Reasoning`, and a positive `Context`, whether it is the default or an alternative (R-E5FU-SAHM); an embedding entry's terms live in `EmbeddingInfo` and its offerings carry the route and context. A route whose terms have not been established is expressed by **not listing the offering** — never by a nil cell, which would tell the consumer a route exists on terms they must guess. The earlier tiered-audit rule (secondary offerings allowed blank) is deleted: it was an oversight against the catalog's own purpose, since a consumer holding a blank offering is exactly the guessing the catalog exists to prevent. `nil` remains representable in the types on purpose — it is the honest authoring zero, and the shipped-data tests are what reject it, the same way the other data invariants are enforced.

**Every offering carries real rates — including routes that report their own cost.** An earlier version of this decision waived pricing on OpenRouter offerings because D16 resolves runtime cost from `RoundTrip.ReportedCost()` first. That waiver is reversed (operator decision): the fact that the route reports its charge is precisely what makes establishing its rate table cheap, and having the rate in the catalog means **all information needed to pick a model is present at picking time**, before any request is sent. The runtime precedence is unchanged — reported cost still wins on the wire (D16); the catalog cell serves prediction and pickers. The audited rate tables live in research §6.5, including the OpenRouter route table.

**A reasoning spec states what is documented and confirmed — never what a gateway tolerates.** The audit (research §14.7) established that OpenRouter's parser returns 200 for effort values, budgets, and toggles a model does not honor, so wire acceptance establishes nothing. The authoring rule for every offering's spec cells, in precedence order:

1. **Documented and confirmed.** The serving provider's own per-model documentation (for OpenRouter: the `reasoning` descriptor its models endpoint publishes per model, supplemented by its prose docs), confirmed to work on that route. Confirmation means a deterministic signal — an off-form's hard rejection, an enforced bound, a matching observation — not a 200.
2. **Ambiguity resolves toward the native provider.** Where the route's documentation is silent, generic, contradictory, or unconfirmed, the model is assumed to behave as its native provider documents, since a router most plausibly passes through. A router that documents its *own* divergent vocabulary for a model (proving it does not pass through) wins over native for those cells.
3. **Never from acceptance alone.** A value the gateway merely tolerates is not part of the valid set.

The resolved per-route cells this rule produces for the current data are recorded in research §14.7's resolved offering table; the shipped data transcribes it.

**Router coverage: every tracked chat model lists its OpenRouter offering.** The catalog's coverage policy (operator decision) is that a tracked chat model carries an offering for each supported provider that serves it — today its native provider and OpenRouter, whose live model list serves all 26 tracked chat models (research §14.7). This is what makes the catalog complete for a consumer holding only an OpenRouter key: `Lookup` on any tracked model shows the OpenRouter route with its full terms. Whether OpenRouter serves a model is an external fact, so the policy is enforced two ways: a shipped-data check that every chat entry carries a `ProviderOpenRouter` offering (R-EBJC-P573), and the live round-trip check (R-4NJ4-SJ41) that each such route actually serves.

**The wire name is derived, never authored — except where the provider broke the convention, and then it is data.** Each provider has a naming rule, and the id sent on the wire is that rule applied to the entry: OpenRouter joins vendor and model with a slash (`x-ai/grok-4.5`, `z-ai/glm-5.2`); a direct provider sends the model name verbatim. The rule lives in code, not in a format template. The audit surfaced the first genuine irregularity: OpenRouter spells exactly three tracked Anthropic models with dots (`anthropic/claude-opus-4.8`, `anthropic/claude-sonnet-4.6`, `anthropic/claude-haiku-4.5`) where the catalog key — Anthropic's own id — is hyphenated, so the derived join names a route OpenRouter does not serve. The escape hatch this decision previously reserved for that event is now real: an offering's optional `WireName`, **empty for every offering that follows the convention** (derive as always) and set verbatim on exactly the offerings that break it (today: those three). The override is consulted only after the offering is matched by `Provider` — it never influences which offering resolves — and a wrong or stale cell is falsified by the live round-trip check, which uses the same reported wire names (R-4NJ4-SJ41).

**Vendor spellings are OpenRouter's spellings, and the two id sets agree.** `VendorID` uses `x-ai`, `z-ai`, `moonshotai`, `deepseek` because that is what OpenRouter's namespace contains and the join must be exact. Where a vendor also has a provider package the two strings are identical, which keeps the join free of a mapping table. That agreement is why `agentkit.ProviderZAI` is `"z-ai"` rather than `"zai"` — the Go package stays `zai`, since hyphens are not legal in identifiers, but the id it reports is the vendor's spelling (R-LXFD-GS3B).

**The offering order is decided when the catalog is authored; what ships is just a list.** The rule the author applies: the model's own vendor first when we have a provider package for it, then routers in a declared precedence (today only OpenRouter; a second router takes an explicit position when we add one). None of that reasoning ships. At runtime there is an ordered slice, the first element is the default, and the rest are alternatives — no precedence table, no direct-versus-router flag, no credential-awareness. The catalog is static and credential-blind by construction; a consumer that wants to fall back because it holds one key and not another does that one layer up, which is why `Offerings` is a first-class call. What the code can check is the part that matters most in practice — an offering whose provider matches the entry's vendor is the direct route and must sort first, which catches the realistic mistake of appending a direct offering to an existing list (R-LW7H-30CM).

**Auth mode is not a provider.** An offering's `Provider` is an `agentkit.ProviderID` — a provider *package* — never an `agentkit.AuthMode`, never a rendered `Identity` label (D9). The two are separate types precisely so the mistake is a compile error rather than a convention, and a shipped-data check pins the values to the exported constant set (R-LTRO-BGV8). This matters because the subscription path varies none of the terms an offering exists to carry: D25 settles that its cost basis is the same notional API-rate-equivalent resolved the same way, the wire shape and model strings are identical, and the one thing that genuinely differs — which models the backend will serve — is the vendor's loud rejection, not a catalog gate. A consumer's auth choice composes with the catalog without either knowing about the other: the catalog answers where a model can go, the consumer's credential answers how it pays.

**The data.** The catalog ships the maintained tables: per-offering chat rates (nano-USD `RateTier`s, including context-tiered models), reasoning specs, context sizes, wire-name overrides, and embedding rates/capabilities, for the models we track. Rates and reasoning cells are a release-time re-verification item owned by the plan/release process. The authoritative values are pinned by **golden tests inside the package**: the shipped Go data and the recorded reference table cannot silently diverge (R-DQ16-AQWE). This decision deliberately does not restate the full tables; they are data, versioned with the package, edited in one place. The gathered source values live in research §6.5 (rates, including the OpenRouter route table) and §7.1/§14.7 (reasoning vocabularies, native and OpenRouter).

**Wire names are a live-substrate claim.** That a reported name is *well-formed* is checkable offline; that it names a model the provider actually serves is not — a golden test compares the table against itself and a mocked transport accepts whatever it is handed. Cataloging a retired model, misspelling a vendor so the join produces a plausible-but-wrong namespace, or letting an override cell go stale is invisible to every hermetic test in the suite. OpenRouter offerings therefore carry an integration-gated check that drives the real API and observes a completed round trip per offering (R-4NJ4-SJ41). That check **enumerates its subjects from the catalog** rather than from a hardcoded list: a literal list is a second copy of the data that can drift from `data.go` silently, which would leave the one test that can falsify the claim testing something else.

**The default is descriptive, never applied.** AgentKit sends no reasoning fields on an unset value (D6), so what a consumer gets by saying nothing is precisely what the vendor API would have given them. `Default` records that observed behavior so a consumer can *predict* the cost before sending; nothing reads it into a request, and no phase may make it do so. This is what keeps the recorded default true rather than aspirational: the catalog describes the provider, it does not configure it.

**Three shapes of default, because one of them is not a value.** A provider's behavior on silence is `DefaultOff`, `DefaultFixed` (equivalent to sending `Value`), or `DefaultDynamic` (the provider decides per request and the caller has no say). Only the middle one is expressible as a `ReasoningValue`, which is why `Default` is its own type. Two entries prove the split is real rather than pedantic: `deepseek-v4-flash` reasoned on 1 of 3 and then 2 of 3 identical requests, so no fixed value exists to record; and `gemini-2.5-pro`'s default is *also* exactly `Budget(-1)`, yet recording it that way would force a reader to decode a magic integer against `Sentinels` to learn who is in control. `Sentinels` says `-1` is *sendable*; `DefaultDynamic` says the provider *chooses*. Those are two facts and they live in two fields.

**`DefaultUnaudited` is the zero value on purpose — and it never ships, anywhere.** Before the mode split, an offering nobody had probed was indistinguishable from one measured as off, so unaudited data read as a positive claim. Making the zero value mean "unknown" turns that silent ambiguity into a mechanically detectable one, and with the unaudited tier deleted the detection is total: **no shipped offering** carries `Default.Mode == DefaultUnaudited` (R-E6NR-628B). An offering whose default has not been established is an offering that does not ship.

**Enable-ability and disable-ability are two permissions.** `CanEnable` and `CanDisable` are independent bools because the wire treats them independently: `grok-4.5`, `grok-4.20-multi-agent` and `kimi-k2.7-code` accept an explicit on and reject off with a 400, while `grok-4.20` accepts both and defaults to off. `CanEnable` is meaningful only for `Kind: Toggle` — on an enum or range you turn reasoning on by naming a level or a budget, so a separate bool would restate what `Levels`/`Min`/`Max` already say (R-DK0D-JIP0).

**Off-ness is stored, not derived — and the range-derivation consistency is a native-route fact.** `CanDisable` is measured everywhere: a toggle's off-form may simply be rejected, and on an enum nothing but convention separates `gpt-5.4`'s `none` (genuinely off) from `gemini-3.5-flash`'s `minimal` (a floor, not off). For a **native** `Kind: Range` offering, off-ness *is* also derivable — reasoning can be disabled exactly when zero is reachable, via `Min == 0` or an off sentinel (`gemini-2.5-flash` versus `gemini-2.5-pro`) — and that stored-plus-derived redundancy is pinned by a consistency test so the two cannot drift (R-EABG-BDGE). The check is scoped to native providers because on an OpenRouter range offering the off-form is the router's own documented `enabled: false` toggle, independent of the budget vocabulary: `claude-haiku-4-5`'s OpenRouter route has `Min: 1024`, no off sentinel, and `CanDisable: true` — measured, correct, and outside the derivation.

Settled choices:
- **Keyed by model name; names assumed unique.** The primary consumer query is "user typed one string" — a compound key would demand the provider *before* the lookup, defeating resolution. Uniqueness is assumed, not policed (operator decision — no duplicate-detection machinery).
- **An ordered list of offerings, not a default plus a route map.** The two questions a consumer asks — where can this go, and on what terms — are answered by one call returning one ordered slice.
- **`Vendor` is its own type, distinct from `ProviderID`.** xAI, DeepSeek, and Moonshot have no provider package, so folding them into `ProviderID` would put non-providers into the type that names providers.
- **The user never types a wire name.** `grok-4.5` alone resolves to the OpenRouter offering; `openrouter` plus `claude-opus-4-8` resolves to that route's dotted slug. The provider-namespaced form is an implementation detail of the route, derived — or stored, for the exceptions — on the way out.
- **`Kind` stays a single value per offering.** The audit showed no route whose documented-and-confirmed vocabulary spans two kinds: OpenRouter's per-model descriptor documents at most one value form per route, family-level prose claims contradicted by the native provider fail the ambiguity rule, and the gateway's tolerance of every form is not documentation (operator decision). A future route that genuinely documents two confirmed forms reopens this; it is not pre-built.
- **Advisory, structurally enforced.** Root and provider packages never import `catalog` (R-DR92-OIN3); the request path cannot consult it even by accident. Consumers alone wire its data into `Conversation.Pricing`, `Embedder.Pricing`, `Gen.Reasoning` defaults, and `ProviderOptions`.
- **Typed builders live here, not in core.** Vendor-shaped conveniences (`openrouterx.Routing`) emit the same opaque fragments a consumer could write by hand — comfort without closing the escape hatch.
- **Uncataloged ⇒ pass-through, everywhere.** Every helper degrades to "here's your string back, no metadata" — the catalog can never become a gate. `Coverage` names which degradation happened; none of them blocks a call.

**Rejected.**
- *A scalar `Provider` plus `Routes map[string]string`* — the previous shape: rates and reasoning could not vary by route even though they do; the direct provider was implicit; `Provider` did double duty as "who made it" and "who serves it".
- *The tiered audit rule (secondary offerings may carry nil terms)* — this decision's own previous stance, reversed as an oversight: a listed route with unstated terms is exactly the consumer-guessing the catalog exists to prevent. Unestablished routes are unlisted, not blank.
- *Waiving pricing where the provider reports cost (the previous OpenRouter stance)* — reversed: the reported cost makes the rate cheap to establish, and picking a model needs the rate before any response exists. Runtime reported-cost precedence (D16) is untouched.
- *Reading the valid reasoning set off wire acceptance* — OpenRouter's parser 200s values a model does not honor (research §14.7); acceptance is not knowledge. Documented-and-confirmed is the bar.
- *Multi-kind reasoning specs (dropping `Kind` for populated-fields form declaration)* — proposed when router prose suggested dual vocabularies; rejected once the per-model descriptor + ambiguity rule showed no confirmed dual-form route exists. Machinery for a case the data does not contain.
- *Storing every wire name on every offering* — ~23 hand-written strings to accommodate 3 exceptions; kills the derivation convention and reintroduces the transcription-slip class it deleted. The override cell is data only where the convention is broken.
- *A format-template string per provider (`"{vendor}/{model}"`)* — moves the naming rule into strings the compiler cannot check.
- *Offering keys that name a credential mode (`openai.subscription`)* — reintroduces the wire × auth name explosion D5 rejected (D25).
- *Inheriting the native offering's reasoning terms into a router offering* — states a measured-looking falsehood; the audit proved router vocabularies genuinely diverge (`glm-5.2`: native `high,max` vs OpenRouter's documented `high,xhigh`).
- *Credential-aware default selection inside the catalog* — static data plus `Offerings` lets the layer that knows the keys pick.
- *A runtime precedence table and a direct/router flag* — scaffolding for computing an order the author already decided.
- *`Default` typed as `agentkit.ReasoningValue`* — false for every provider whose default is an opaque or per-request policy.
- *A portable `Dynamic()` constructor on `ReasoningValue`* — dynamic is natively sendable on exactly two Gemini models; exposing it portably would synthesize a concept most providers lack (D6).
- *One fixed default applied everywhere (e.g. `medium`)* — many tracked models have no levels to receive it; several default off; `gemini-2.5-pro` has no off at all.
- *Deriving `CanDisable` from `Min`/`Sentinels` for ranges instead of storing it* — makes one field mean "measured" on toggles and enums but "inferred" on ranges; and on router ranges the derivation is simply wrong (the off-form is the router's toggle).
- *A universal range-derivation consistency check* — the previous, unscoped form of R-EABG-BDGE; falsified by `claude-haiku-4-5`'s OpenRouter route, where `CanDisable: true` coexists with `Min: 1024` because OpenRouter's `enabled: false` is the off-form.
- *Folding `CanEnable` into `CanDisable` as a single tri-state* — they are independent permissions the wire grants separately.
- *Compound (provider, model) keys* — demands the provider before the primary lookup; operator-rejected.
- *Duplicate-key golden policing* — machinery for a collision the naming conventions make hypothetical (operator decision).
- *Exported per-provider model constants* — a second driftable model list; discoverability is catalog data rendered by consumers.
- *Catalog consulted by the orchestrator (auto-pricing on Send)* — re-couples running to catalog coverage through the back door.
- *Per-provider inspector interfaces* — one data package with plain lookups replaces N interface implementations.

**Verification.**
- R-DMDH-5FOB — `Lookup` on a cataloged chat model returns its vendor and its offerings; on a cataloged embedding model returns its `EmbeddingInfo`; on an unknown name returns `ok=false` — all with no network, no credentials, and no client construction.
- R-LOW2-SDWG — every shipped entry has a non-empty `Offerings` slice, and `Lookup` returns the offerings in their authored order with `Offerings[0]` equal to what `Resolve("", model)` selects. Reordering an entry's offerings changes which offering `Resolve("", model)` returns, proving the order is load-bearing rather than incidental.
- R-LRBV-JXDU — `Offerings(m)` returns that model's offerings in order and `nil` for an uncataloged name; `Offer(m, p)` returns the offering whose provider is `p` with `ok=true`, and `ok=false` for a provider the model has no offering for. For a multi-offering model the two agree: `Offer(m, Offerings(m)[i].Provider)` equals `Offerings(m)[i]`.
- R-DNLD-J7F0 — `Resolve` covers its three states: a cataloged model with no provider named resolves to `Offerings[0]` with `Coverage == Curated`; a cataloged model with a named provider that has an offering resolves to *that* offering's terms; a named provider with no offering (cataloged model or not) returns the model name verbatim with `Coverage == Passthru` and a zero `Offering`; and no provider named on an uncataloged model returns `Coverage == Unrouted` with an empty `Provider`. No input errors and no input is blocked.
- R-E7VN-JTZ0 — wire-name precedence: for an offering with a non-empty `WireName`, `Entry.WireModel` and `Resolution.WireModel` return it verbatim (`claude-opus-4-8` on `openrouter` → `anthropic/claude-opus-4.8`); for an empty `WireName` they derive — `Vendor + "/" + Model` for `ProviderOpenRouter` (`grok-4.5` → `x-ai/grok-4.5`), the model name verbatim for a direct provider — and changing an entry's `Vendor` changes only its *derived* OpenRouter name, proving derivation stores nothing. In the shipped data, exactly the three dotted Anthropic OpenRouter offerings (`claude-opus-4-8`, `claude-sonnet-4-6`, `claude-haiku-4-5`) carry a non-empty `WireName`.
- R-LXFD-GS3B — for every `VendorID` the catalog ships that also names a provider package, the `VendorID` and the corresponding `agentkit.ProviderID` are the identical string — pinning `z-ai` on both sides, so the OpenRouter join needs no mapping. A vendor with no provider package (`x-ai`, `deepseek`, `moonshotai`) is exempt and asserted to have no matching `ProviderID`.
- R-LTRO-BGV8 — every shipped offering's `Provider` is one of the exported `agentkit.ProviderID` constants. An offering keyed by a credential-mode label or a misspelled provider fails this.
- R-LW7H-30CM — for every shipped entry, if any offering's `Provider` equals the entry's `Vendor` (compared as strings), that offering is `Offerings[0]`. Moving `glm-5.2`'s `z-ai` offering behind its `openrouter` offering fails this.
- R-E5FU-SAHM — completeness: every shipped chat offering — `Offerings[0]` and every alternative alike — carries a non-nil `Pricing` with at least one `RateTier`, a non-nil `Reasoning`, and `Context > 0`; every shipped embedding offering carries `Context > 0`. A nil cell anywhere in shipped data fails the suite.
- R-EBJC-P573 — router coverage: every shipped chat entry carries an offering whose provider is `agentkit.ProviderOpenRouter`. A tracked chat model with no OpenRouter route in its offerings fails this. (Embedding entries are exempt — OpenRouter is not an embedding provider.)
- R-DOT9-WZ5P — `ListCurated(p)` returns every entry carrying an offering whose provider is `p`, and nothing else; a provider with no offerings anywhere returns an empty list.
- R-DQ16-AQWE — golden: the shipped catalog data (each offering's provider, `WireName`, `RateTier` values, reasoning spec including every `Kind`, `Levels`, `Min`/`Max`, `Sentinels`, `CanEnable`, `CanDisable` and `Default` cell, context size, each entry's vendor and offering order, embedding rates and capability rows) equals the package's recorded reference table, so a transcription slip cannot ship silently.
