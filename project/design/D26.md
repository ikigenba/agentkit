# Decision 26 — The advisory model catalog: `agentkit/catalog`

**Decision.** All model knowledge evicted from the provider layer (D5) lives in **one advisory data package, `agentkit/catalog`**: maintained reference data about known models — chat and embedding — plus lookup helpers and typed option builders. It is **consumer-facing only**: nothing in root `agentkit` or any provider package imports it, and nothing in the request path consults it. Its absence for a model restricts nothing (free-flow); its presence makes the common path effortless.

The catalog's unit of knowledge is the **offering** — one model as served by one provider. A model is keyed by name and carries an **ordered list** of the offerings that can serve it: `Offerings[0]` is the default, and the rest are the valid alternatives. Terms that differ by route — rates, reasoning vocabulary, context size, provider options — live on the offering, because they are facts about a *(model, provider)* pair and not about a model.

```go
// package catalog

// Entry is everything the catalog knows about one model, keyed by its model
// name. Model names are assumed globally unique.
type Entry struct {
    Model     string     // the key: "claude-opus-4-8", "glm-5.2", "text-embedding-3-small", …
    Vendor    VendorID   // who built the model — not necessarily anyone who serves it
    Offerings []Offering // ordered by preference; [0] is the default. Never empty.
    Embedding *EmbeddingInfo // embedding entries: rates + capabilities (nil for chat entries)
}

// Offering is one model as served by one provider, with that route's own terms.
// Pricing and Reasoning are nil where the catalog has not audited this route;
// Offerings[0] always carries both for a chat entry (see the tiered audit rule).
type Offering struct {
    Provider  agentkit.ProviderID // always a provider package, never a credential mode (D9)
    Pricing   *agentkit.Pricing   // this route's rates — for Conversation.Pricing
    Reasoning *ReasoningSpec      // this route's reasoning vocabulary + default
    Context   int64               // context-window tokens (advisory display/budgeting)
    Options   json.RawMessage     // default ProviderOptions fragment, when one is advisable
}

// VendorID names who built a model. Its values are spelled exactly as
// OpenRouter spells its vendor namespaces, so the OpenRouter wire name is a
// pure join with no mapping table (see "the wire name is derived").
type VendorID string
const (
    VendorAnthropic VendorID = "anthropic"
    VendorOpenAI    VendorID = "openai"
    VendorGoogle    VendorID = "google"
    VendorZAI       VendorID = "z-ai"
    VendorXAI       VendorID = "x-ai"
    VendorDeepSeek  VendorID = "deepseek"
    VendorMoonshot  VendorID = "moonshotai"
)
```

```go
// ReasoningSpec describes one offering's native reasoning vocabulary — the data
// that lets a consumer render, validate, and default reasoning up front
// (D6: validation is advisory, never in the request path). It answers three
// independent questions, and keeps them in three separate places: what values
// may be sent (Levels / Min,Max / Sentinels), which explicit switches the model
// accepts (CanEnable, CanDisable), and what the provider does when nothing is
// sent (Default).
type ReasoningSpec struct {
    Term       string           // "effort" | "thinking level" | "thinking budget" | "thinking"
    Kind       ReasoningKind    // Enum | Range | Toggle
    Levels     []string         // Kind==Enum
    Min, Max   int              // Kind==Range
    Sentinels  []Sentinel       // Range magic values (0=off, -1=dynamic)
    CanEnable  bool             // an explicit on-form exists and the model accepts it (Kind==Toggle only)
    CanDisable bool             // an explicit off-form exists and the model accepts it
    Default    ReasoningDefault // what the provider does on an unset value
}
type ReasoningKind int
const ( ReasoningEnum ReasoningKind = iota; ReasoningRange; ReasoningToggle )
type Sentinel struct{ Value int; Meaning string }

// ReasoningDefault answers "what happens if I send nothing?" — deliberately a
// different type from agentkit.ReasoningValue, which answers "what may I send?".
// Not every provider default is expressible as a value the caller could have
// sent, so typing the default as a ReasoningValue forces a false claim.
type ReasoningDefault struct {
    Mode  ReasoningDefaultMode
    Value agentkit.ReasoningValue // set only when Mode == DefaultFixed
}
type ReasoningDefaultMode int
const (
    DefaultUnaudited ReasoningDefaultMode = iota // zero value: neither measured nor sourced
    DefaultOff                                   // does not reason unless asked
    DefaultFixed                                 // equivalent to the caller sending Value
    DefaultDynamic                               // provider chooses per request; not caller-controllable
)

// EmbeddingInfo carries an embedding model's rates and capabilities.
type EmbeddingInfo struct {
    Pricing         agentkit.EmbeddingPricing
    NativeDimension int
    MinDimension    int // inclusive producible lower bound
    MaxDimension    int // == NativeDimension
    MaxInputTokens  int // advisory; the provider is the enforcer (D19)
}
```

```go
// Lookup returns the entry for a model name; ok=false for an uncataloged name
// (which remains fully runnable — the caller just gets no conveniences).
func Lookup(model string) (Entry, bool)

// Offerings returns the ordered offerings for a model — [0] the default, the
// rest the valid alternatives — each already carrying that route's rates,
// reasoning vocabulary, and context size. One call answers "where can this
// model go, and on what terms." Nil for an uncataloged model.
func Offerings(model string) []Offering

// Offer returns one model's offering for a named provider, for callers that
// already hold a provider name from elsewhere (a -provider flag, a running
// handle's Identity). Same data the list carries.
func Offer(model string, provider agentkit.ProviderID) (Offering, bool)

// WireModel derives the id a provider is sent on the wire for this entry.
func (e Entry) WireModel(provider agentkit.ProviderID) string

// Resolve answers the two-axis query (a consumer's -provider/-model pair)
// without ever rejecting free-form input. Coverage states how much the catalog
// knows; no value of it blocks a call.
func Resolve(provider agentkit.ProviderID, model string) Resolution

type Resolution struct {
    Vendor    VendorID
    Provider  agentkit.ProviderID
    WireModel string
    Offering  Offering // zero unless Coverage == Curated
    Coverage  Coverage
}

type Coverage int
const (
    Curated  Coverage = iota // an offering matched; terms are whatever it carries
    Passthru                 // a provider was named that has no offering; model sent verbatim
    Unrouted                 // no provider named and no entry; the catalog has no default to give
)

// ListCurated enumerates every entry carrying an offering for a provider —
// catalog rendering for pickers/--help. It reports what the catalog covers,
// never what the provider can serve.
func ListCurated(provider agentkit.ProviderID) []Entry

// Check validates a ReasoningValue against one offering's spec — advisory
// pre-flight for consumers that want errors before spending a round trip. The
// provider argument is required because two offerings of one model may carry
// different vocabularies. ok=false: no offering, nothing to check against.
func Check(model string, provider agentkit.ProviderID, v agentkit.ReasoningValue) (accepted bool, spec *ReasoningSpec, ok bool)
```

```go
// package catalog/openrouterx — typed builder over the ProviderOptions escape
// hatch (D9/D24): convenience, never a gate; unknown future knobs are written
// raw alongside it.

type Routing struct {
    Order          []string
    Only, Ignore   []string
    Sort           string   // "price" | "throughput" | "latency"
    MaxPrice       *MaxPrice
    Quantizations  []string
    ZDR            bool
    AllowFallbacks *bool
}
func (r Routing) ProviderOptions() json.RawMessage // emits {"provider":{...}}
```

**The wire name is derived, never authored.** Each provider has a naming rule, and the id sent on the wire is that rule applied to the entry. OpenRouter joins vendor and model with a slash (`x-ai/grok-4.5`, `z-ai/glm-5.2`, `moonshotai/kimi-k3`); a direct provider sends the model name verbatim. All thirteen OpenRouter-reachable models we track follow the join exactly, with the model half equal to the catalog key in every case, so storing the slug stored thirteen strings that a two-argument function computes. Deriving deletes them, deletes the transcription slip that let a bare id reach OpenRouter, and makes adding a model a matter of naming its vendor rather than looking up a namespace (R-LQ3Z-65N5). The rule lives in code, not in a format template: a template language is machinery for a handful of providers and moves the logic into strings the compiler cannot check. A provider whose naming needs inputs the entry does not carry (a region, a version suffix) gets its own function, and whatever data it needs, when we support it.

**Vendor spellings are OpenRouter's spellings, and the two id sets agree.** `VendorID` uses `x-ai`, `z-ai`, `moonshotai`, `deepseek` because that is what OpenRouter's namespace contains and the join must be exact. Where a vendor also has a provider package the two strings are identical, which is what makes the authoring rule below a literal string comparison and keeps the join free of a mapping table. That agreement is why `agentkit.ProviderZAI` is `"z-ai"` rather than `"zai"` — the Go package stays `zai`, since hyphens are not legal in identifiers, but the id it reports is the vendor's spelling (R-LXFD-GS3B).

**The offering order is decided when the catalog is authored; what ships is just a list.** The rule the author applies: the model's own vendor first when we have a provider package for it, then routers in a declared precedence (today only OpenRouter; a second router takes an explicit position when we add one). None of that reasoning ships. At runtime there is an ordered slice, the first element is the default, and the rest are alternatives — no precedence table, no direct-versus-router flag, no credential-awareness. The catalog is static and credential-blind by construction; a consumer that wants to fall back because it holds one key and not another does that one layer up, which is why `Offerings` is a first-class call.

Moving the rule to authoring time means the code cannot check the ordering itself. What it can check is the part that matters most in practice — an offering whose provider matches the entry's vendor is the direct route and must sort first, which catches the realistic mistake of appending a direct offering to an existing list (R-LW7H-30CM). Router precedence among two or more routers is genuinely convention plus review.

**Terms live on the offering, and secondary offerings may be blank.** `Offerings[0]` of a chat entry always carries a `Pricing` and a `ReasoningSpec`: it is the common path, it is what `Resolve("", model)` returns, and a blank there would undo everything the reasoning descriptor establishes. A secondary offering may carry `nil` for either, meaning the catalog has not audited that route (R-LSJR-XP4J). `nil` stays honest because it is visibly nothing rather than a zero value masquerading as a measurement — the same reason `DefaultUnaudited` is the zero mode. Copying the default offering's terms across would be worse than blank: OpenRouter normalizes reasoning into its own parameter shape, so z-ai's native `effort (+ toggle)` vocabulary is not what the OpenRouter route accepts, and inheriting it would state a measured-looking falsehood. For an OpenRouter offering `nil` pricing is not even a gap: D16 resolves cost from `RoundTrip.ReportedCost()` first, and OpenRouter reports the charge on every response, so a maintained table of its margins would be data we carry and never read.

**Auth mode is not a provider.** An offering's `Provider` is an `agentkit.ProviderID` — a provider *package* — never an `agentkit.AuthMode`, never a rendered `Identity` label (D9). The two are separate types precisely so the mistake is a compile error rather than a convention, and a shipped-data check pins the values to the exported constant set (R-LTRO-BGV8). This matters because the subscription path varies none of the terms an offering exists to carry: D25 settles that its cost basis is the same notional API-rate-equivalent resolved the same way, the wire shape and model strings are identical, and the one thing that genuinely differs — which models the backend will serve — is the vendor's loud rejection, not a catalog gate. A consumer's auth choice composes with the catalog without either knowing about the other: the catalog answers where a model can go, the consumer's credential answers how it pays.

**The data.** The catalog ships the maintained tables: per-offering chat rates (nano-USD `RateTier`s, including context-tiered models), reasoning specs, context sizes, and embedding rates/capabilities, for the models we track. Rates and any estimated reasoning cells are a release-time re-verification item owned by the plan/release process. The authoritative values are pinned by **golden tests inside the package**: the shipped Go data and the recorded reference table cannot silently diverge (R-DQ16-AQWE). This decision deliberately does not restate the full tables; they are data, versioned with the package, edited in one place. The gathered source values live in research §6.5 (rates) and §7.1 (reasoning vocabularies).

**Wire names are a live-substrate claim.** That a derived name is *well-formed* is checkable offline; that it names a model the provider actually serves is not — a golden test compares the table against itself and a mocked transport accepts whatever it is handed. Cataloging a retired model, or misspelling a vendor so the join produces a plausible-but-wrong namespace, is invisible to every hermetic test in the suite. OpenRouter offerings therefore carry an integration-gated check that drives the real API and observes a completed round trip per offering (R-4NJ4-SJ41). That check **enumerates its subjects from the catalog** rather than from a hardcoded list: a literal list is a second copy of the data that can drift from `data.go` silently, which would leave the one test that can falsify the claim testing something else.

**The default is descriptive, never applied.** AgentKit sends no reasoning fields on an unset value (D6), so what a consumer gets by saying nothing is precisely what the vendor API would have given them. `Default` records that observed behavior so a consumer can *predict* the cost before sending; nothing reads it into a request, and no phase may make it do so. This is what keeps the recorded default true rather than aspirational: the catalog describes the provider, it does not configure it.

**Three shapes of default, because one of them is not a value.** A provider's behavior on silence is `DefaultOff`, `DefaultFixed` (equivalent to sending `Value`), or `DefaultDynamic` (the provider decides per request and the caller has no say). Only the middle one is expressible as a `ReasoningValue`, which is why `Default` is its own type. Two entries prove the split is real rather than pedantic: `deepseek-v4-flash` reasoned on 1 of 3 and then 2 of 3 identical requests, so no fixed value exists to record; and `gemini-2.5-pro`'s default is *also* exactly `Budget(-1)`, yet recording it that way would force a reader to decode a magic integer against `Sentinels` to learn who is in control. `Sentinels` says `-1` is *sendable*; `DefaultDynamic` says the provider *chooses*. Those are two facts and they live in two fields.

**`DefaultUnaudited` is the zero value on purpose.** Before this split, an offering that nobody had probed was indistinguishable from one measured as off, so unaudited data read as a positive claim. Making the zero value mean "unknown" turns that silent ambiguity into a mechanically detectable one (R-DMG6-B26E), consistent with failing loudly rather than defaulting quietly.

**Enable-ability and disable-ability are two permissions.** `CanEnable` and `CanDisable` are independent bools because the wire treats them independently: `grok-4.5`, `grok-4.20-multi-agent` and `kimi-k2.7-code` accept an explicit on and reject off with a 400, while `grok-4.20` accepts both and defaults to off. `CanEnable` is meaningful only for `Kind: Toggle` — on an enum or range you turn reasoning on by naming a level or a budget, so a separate bool would restate what `Levels`/`Min`/`Max` already say (R-DK0D-JIP0).

**Off-ness is stored, not derived, even where it is derivable.** For `Kind: Range` it *is* derivable — reasoning can be disabled exactly when zero is reachable, either through `Min == 0` or an off sentinel — and `gemini-2.5-flash` (`Min: 0`) versus `gemini-2.5-pro` (`Min: 128`, every legal request still thinks) is that derivation in action. It is not derivable for the other two shapes: a toggle's off-form may simply be rejected, and on an enum nothing but convention separates `gpt-5.4`'s `none` (genuinely off) from `gemini-3.5-flash`'s `minimal` (a floor, not off). A field that meant "measured" on two shapes and "inferred" on a third would be a trap, so `CanDisable` is measured everywhere and the range case is pinned by a consistency test (R-DL89-XAFP) that makes the redundancy impossible to get wrong.

Settled choices:
- **Keyed by model name; names assumed unique.** The primary consumer query is "user typed one string" — a compound key would demand the provider *before* the lookup, defeating resolution. Uniqueness is assumed, not policed (operator decision — no duplicate-detection machinery).
- **An ordered list of offerings, not a default plus a route map.** The two questions a consumer asks — where can this go, and on what terms — are answered by one call returning one ordered slice. The previous shape answered the first with a scalar `Provider` plus a `Routes` map that omitted the direct route, so "which providers serve this" required unioning two fields and no exported function did it; and it answered the second with model-level `Pricing`/`Reasoning` that could not vary by route at all.
- **`Vendor` is its own type, distinct from `ProviderID`.** xAI, DeepSeek, and Moonshot have no provider package, so folding them into `ProviderID` would put non-providers into the type that names providers. Separate types keep "who built it" and "who serves it" from being confusable, and record the fact the previous shape stated falsely: `grok-4.5` was `Provider: "openrouter"`, which is not true of xAI.
- **The user never types a wire name.** `grok-4.5` alone resolves to the OpenRouter offering; `openrouter` plus `grok-4.5` resolves to the same one. The vendor-namespaced form is an implementation detail of the route, derived on the way out.
- **Advisory, structurally enforced.** Root and provider packages never import `catalog` (R-DR92-OIN3); the request path cannot consult it even by accident. Consumers alone wire its data into `Conversation.Pricing`, `Embedder.Pricing`, `Gen.Reasoning` defaults, and `ProviderOptions`.
- **Typed builders live here, not in core.** Vendor-shaped conveniences (`openrouterx.Routing`) emit the same opaque fragments a consumer could write by hand — comfort without closing the escape hatch.
- **Uncataloged ⇒ pass-through, everywhere.** Every helper degrades to "here's your string back, no metadata" — the catalog can never become a gate. `Coverage` names which degradation happened; none of them blocks a call.

**Rejected.**
- *A scalar `Provider` plus `Routes map[string]string`* — the previous shape. The route map carried a wire slug and nothing else, so rates and reasoning could not vary by route even though they do; the direct provider was implicit and absent from the map, so enumerating a model's providers meant unioning two fields; and `Provider` did double duty as "who made it" and "who serves it", forcing `grok-4.5` to claim OpenRouter as its vendor. Adding a second router with its own rates and naming rule has nowhere to go in it.
- *Storing the wire name on the offering* — thirteen hand-written strings a two-argument function computes exactly, plus the transcription slip (a bare id where a namespaced slug belongs) and the test that guarded it. Derivation deletes all three.
- *A format-template string per provider (`"{vendor}/{model}"`)* — more general than a function and worse: it moves the naming rule into strings the compiler cannot check, for a handful of providers.
- *An explicit wire-name override field on the offering* — a hook for an irregularity that does not exist in any tracked model; add it when something actually breaks the convention (operator decision).
- *Offering keys that name a credential mode (`openai.subscription`)* — reintroduces the wire × auth name explosion D5 rejected, in a package that is credential-blind by construction. The subscription path varies no term an offering carries (D25).
- *Full audit of every offering* — would force measuring the four secondary `glm` routes before this release and copying numbers we cannot stand behind for any route not yet probed. The tiered rule states the true state of our knowledge instead.
- *Inheriting the default offering's terms into an unaudited secondary* — states a measured-looking falsehood; OpenRouter's normalized reasoning parameter is not z-ai's native vocabulary.
- *Credential-aware default selection inside the catalog* — the catalog would have to read the environment to know which key a consumer holds. Static data plus `Offerings` lets the layer that *does* know pick.
- *A runtime precedence table and a direct/router flag* — scaffolding for computing an order the author already decided. What ships is the decision, not the reasoning.
- *`Default` typed as `agentkit.ReasoningValue`* — it can only say "the default equals what you would have got by sending X", which is false for every provider whose default is an opaque or per-request policy, and its zero value conflated "dynamic", "off", and "nobody looked".
- *A portable `Dynamic()` constructor on `ReasoningValue`* — dynamic is natively sendable on exactly two Gemini models (`Budget(-1)`); exposing it portably would make AgentKit synthesize a concept for providers that lack one (D6).
- *One fixed default applied everywhere (e.g. `medium`)* — nine tracked models have no levels to receive it, six default to off so injecting a level silently turns reasoning on and bills for it, `gemini-2.5-pro` has no off at all, and genuinely dynamic models have no level to match.
- *Deriving `CanDisable` from `Min`/`Sentinels` for ranges instead of storing it* — makes one field mean "measured" on toggles and enums but "inferred" on ranges.
- *Folding `CanEnable` into `CanDisable` as a single tri-state* — they are independent permissions the wire grants separately.
- *Compound (provider, model) keys* — demands the provider before the primary lookup; operator-rejected.
- *Duplicate-key golden policing* — machinery for a collision the naming conventions make hypothetical (operator decision).
- *Exported per-provider model constants* — a second driftable model list; discoverability is catalog data rendered by consumers.
- *Catalog consulted by the orchestrator (auto-pricing on Send)* — re-couples running to catalog coverage through the back door.
- *Per-provider inspector interfaces (`ReasoningInspector`/`EmbeddingInspector`)* — one data package with plain lookups replaces N interface implementations.

**Verification.**
- R-DMDH-5FOB — `Lookup` on a cataloged chat model returns its vendor and its offerings; on a cataloged embedding model returns its `EmbeddingInfo`; on an unknown name returns `ok=false` — all with no network, no credentials, and no client construction.
- R-LOW2-SDWG — every shipped entry has a non-empty `Offerings` slice, and `Lookup` returns the offerings in their authored order with `Offerings[0]` equal to what `Resolve("", model)` selects. Reordering an entry's offerings changes which offering `Resolve("", model)` returns, proving the order is load-bearing rather than incidental.
- R-LRBV-JXDU — `Offerings(m)` returns that model's offerings in order and `nil` for an uncataloged name; `Offer(m, p)` returns the offering whose provider is `p` with `ok=true`, and `ok=false` for a provider the model has no offering for. For a multi-offering model the two agree: `Offer(m, Offerings(m)[i].Provider)` equals `Offerings(m)[i]`.
- R-DNLD-J7F0 — `Resolve` covers its three states: a cataloged model with no provider named resolves to `Offerings[0]` with `Coverage == Curated`; a cataloged model with a named provider that has an offering resolves to *that* offering's terms; a named provider with no offering (cataloged model or not) returns the model name verbatim with `Coverage == Passthru` and a zero `Offering`; and no provider named on an uncataloged model returns `Coverage == Unrouted` with an empty `Provider`. No input errors and no input is blocked.
- R-LQ3Z-65N5 — `Entry.WireModel` derives rather than looks up: for `ProviderOpenRouter` it returns `Vendor + "/" + Model` (`grok-4.5` → `x-ai/grok-4.5`, `glm-5.2` → `z-ai/glm-5.2`), and for a direct provider it returns `Model` verbatim (`glm-5.2` on `z-ai` → `glm-5.2`). `Resolve` reports the same string in `Resolution.WireModel`. Changing an entry's `Vendor` changes its derived OpenRouter name, proving nothing is stored.
- R-LXFD-GS3B — for every `VendorID` the catalog ships that also names a provider package, the `VendorID` and the corresponding `agentkit.ProviderID` are the identical string — pinning `z-ai` on both sides, so the OpenRouter join needs no mapping. A vendor with no provider package (`x-ai`, `deepseek`, `moonshotai`) is exempt and asserted to have no matching `ProviderID`.
- R-LTRO-BGV8 — every shipped offering's `Provider` is one of the exported `agentkit.ProviderID` constants. An offering keyed by a credential-mode label or a misspelled provider fails this.
- R-LW7H-30CM — for every shipped entry, if any offering's `Provider` equals the entry's `Vendor` (compared as strings), that offering is `Offerings[0]`. Moving `glm-5.2`'s `z-ai` offering behind its `openrouter` offering fails this.
- R-LSJR-XP4J — for every shipped chat entry, `Offerings[0]` carries a non-nil `Pricing` and a non-nil `Reasoning`; a secondary offering may carry `nil` for either, and at least one shipped secondary offering does, proving the tier is real rather than vacuous.
- R-DOT9-WZ5P — `ListCurated(p)` returns every entry carrying an offering whose provider is `p`, and nothing else; a provider with no offerings anywhere returns an empty list.
- R-DQ16-AQWE — golden: the shipped catalog data (each offering's provider, `RateTier` values, reasoning spec including every `Kind`, `Levels`, `Min`/`Max`, `Sentinels`, `CanEnable`, `CanDisable` and `Default` cell, context size, each entry's vendor and offering order, embedding rates and capability rows) equals the package's recorded reference table, so a transcription slip cannot ship silently.
- R-DHKK-RZ7M — across every shipped offering carrying a `ReasoningSpec`, `Default.Value` is non-zero **exactly when** `Default.Mode == DefaultFixed`: a `DefaultOff`, `DefaultDynamic`, or `DefaultUnaudited` offering carries the zero `ReasoningValue`, and a `DefaultFixed` offering never does. A `DefaultDynamic` offering that smuggled in a value (the `gemini-2.5-pro` `Budget(-1)` temptation) fails this.
- R-DISH-5QYB — for every shipped offering whose `Default.Mode == DefaultFixed`, its own spec accepts its default: `spec.Accepts(spec.Default.Value)` is true. A default the model could not have been sent is a contradiction in the data.
- R-DK0D-JIP0 — across every shipped offering, `CanEnable == true` implies `Kind == ReasoningToggle`; no `ReasoningEnum` or `ReasoningRange` offering sets it, since on those shapes on-ness is expressed by naming a level or budget.
- R-DL89-XAFP — across every shipped offering with `Kind == ReasoningRange`, `CanDisable` equals `Min == 0 || <a Sentinel whose Meaning is "off" exists>`. `gemini-2.5-flash` (`Min: 0`, off sentinel) is true and `gemini-2.5-pro` (`Min: 128`, no off sentinel) is false; flipping either cell fails, which is the drift this stored-plus-derived redundancy exists to catch.
- R-DMG6-B26E — no shipped chat entry's `Offerings[0]` has `Default.Mode == DefaultUnaudited`; adding a model without establishing its default fails the suite rather than shipping an unrecorded default that reads as "off". A secondary offering carrying no `ReasoningSpec` at all is the audited way to say "this route is unmeasured".
- R-DNO2-OTX3 — `spec.Accepts(agentkit.EnableReasoning())` is true exactly when `CanEnable` is set, and on a `Kind == ReasoningEnum` or `ReasoningRange` spec it is false regardless of `CanDisable`.
- R-LYN9-UJU0 — `Check(m, p, v)` validates against the offering for `p` specifically: for a model whose two offerings carry different specs, a value native to one and foreign to the other is accepted under the first provider and rejected under the second; `ok=false` when the model has no offering for `p`, with nothing checked.
- R-DOVZ-2LNS — live (integration-gated, real OpenRouter credentials): for each OpenRouter offering, the catalog's `CanDisable` claim matches the real API — sending the wire's off-form returns a completed response for every `CanDisable: true` offering, and is rejected with a provider error for every `CanDisable: false` offering (`grok-4.5`, `grok-4.20-multi-agent`, `kimi-k2.7-code` currently). No hermetic test can falsify this: a mock accepts whichever fragment it is handed, so only the vendor can say whether a model may be switched off.
- R-DR92-OIN3 — structural: neither root `agentkit` nor any provider sub-package imports `agentkit/catalog` (asserted mechanically over the module's import graph), so the request path provably cannot consult it.
- R-4NJ4-SJ41 — live (integration-gated, real OpenRouter credentials): each wire name the catalog derives for an OpenRouter offering is accepted by the real OpenRouter API — a minimal round trip per offering returns a completed response, not a model-not-found error. The subject list is **enumerated from the catalog** (`ListCurated(agentkit.ProviderOpenRouter)` and each entry's derived name), never a literal in the test, so adding an offering extends the live check automatically and a vendor-spelling edit cannot leave a stale copy behind. Skips cleanly without credentials.
- R-DSGZ-2ADS — `openrouterx.Routing.ProviderOptions()` emits exactly the `{"provider":{...}}` fragment its fields describe (order/only/sort/max_price/zdr, omitting unset fields), byte-comparable against hand-written JSON, and the emitted fragment round-trips through `Request.ProviderOptions` merging (R-CXZH-I0UF) unchanged.
