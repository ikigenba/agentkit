# Decision 23 — Deferred tools & the built-in `load_tools` meta-tool

**Decision.** A consumer can register tools as **deferred**: constructed and callable like any `Tool` (Decision 4), but not surfaced to the model up front. Instead, when any deferred tools exist, AgentKit synthesizes one built-in meta-tool, **`load_tools`**, whose *description* carries a generated **catalog** of everything deferred (per-group blurb + bare tool names). The model reads the catalog, calls `load_tools` with exact names, and from the next round-trip on those tools are ordinary members of the live toolset — natively callable, schema conveyed by the provider's own tool-use mechanism. The heavy per-tool descriptions and input schemas stay out of the request until a tool is actually loaded; the resident cost of a large deferred pool is one catalog, paid back per-tool on use.

```go
// DeferredToolGroup is a named set of deferred tools sharing one blurb.
// Groups exist so the generated catalog reads as "server blurb + its tool
// names" (e.g. one group per attached service); a consumer with no grouping
// story passes a single group. Tools are full, callable Tool values — deferral
// changes when they are surfaced to the model, not how they run.
type DeferredToolGroup struct {
    Name  string // catalog section heading, e.g. "crm"
    Blurb string // one-paragraph description of the group; may be ""
    Tools []Tool
}

// On Conversation:
DeferredTools []DeferredToolGroup // empty → no load_tools, behavior unchanged

// The reserved built-in meta-tool, synthesized by the orchestrator whenever
// DeferredTools is non-empty. Input: {"names": ["tool_a", "tool_b"]} — exact
// names only, batched. Its description is generated from the groups.
const loadToolsName = "load_tools"
```

Consumer usage:

```go
conv.Tools = sandboxTools // eager: always in the request
conv.DeferredTools = []agentkit.DeferredToolGroup{
    {Name: "crm", Blurb: crmInstructions, Tools: crmTools},
    {Name: "ledger", Blurb: ledgerInstructions, Tools: ledgerTools},
}
// The model sees sandboxTools + load_tools (whose description catalogs
// crm/ledger); it loads what the task needs and calls it natively.
```

Settled choices:

- **The catalog lives in `load_tools`' own description — no system-prompt injection.** AgentKit composes `Request.System` verbatim from `Conversation.System` (Decision 1) and that stays true: the generated catalog (each group's `Name`, its `Blurb`, and its tools' bare names — *not* their descriptions or schemas) is rendered into the meta-tool's `Description()`. It rides the provider `tools` block, is cache-eligible like any tool definition, and the feature stays entirely inside the tool surface AgentKit already owns.
- **Exact names only, batched — no fuzzy search.** The full catalog is always visible, so the model never needs to *find* a tool, only to *load* it; `load_tools` takes a list of exact names and one call can load several. The result text confirms each load and carries each loaded tool's description + input JSON Schema, so the model can compose a correct native call immediately, before the next round-trip's tools array even arrives. An unknown name yields a per-name error line in the result; the other names in the same call still load; the call is never a terminal failure.
- **Loading is monotonic and conversation-scoped.** A loaded tool stays in the live toolset for the remainder of the `Conversation` — across the rest of the turn *and* subsequent `Send`s. There is no unload verb: unloading would strand `tool_use` blocks in `History` referencing a tool absent from the request (providers reject or degrade on that), and the accumulation this permits is bounded by what the model actually used.
- **Calling a deferred-but-unloaded tool: corrective error + load-on-error.** The orchestrator's tool dispatch distinguishes three cases. *Loaded (or eager)*: run it. *Deferred, not loaded*: do **not** execute the guessed input — the model composed it without ever seeing the schema; feed back a `ToolResultBlock{IsError: true}` whose text names `load_tools` and states the tool has now been loaded, **and load the tool as a side effect**, so recovery is exactly one iteration: the next round-trip carries the real schema and the model retries natively. *Truly unknown* (neither eager, loaded, nor deferred): the existing Decision 10 behavior, an in-band `unknown tool` error result, unchanged.
- **Ordering: frozen sorted base, loads appended in load order — the cache prefix survives.** The orchestrator's request tool order becomes: the name-sorted **base** set (eager `Tools` + MCP-discovered tools + `load_tools` itself), frozen at `Send` exactly as Decision 10 already guarantees, followed by loaded tools **appended in the order they were loaded**. A load therefore only *extends* the serialized tools array; every byte before the new tail is unchanged, so the Anthropic stable-prefix breakpoint (Decision 10) re-reads the old prefix and pays a fresh cache write only for the tail — pay-as-you-go, never a mid-array insertion that invalidates everything after it. Loads made mid-turn are visible from the next round-trip of that same turn (the loop re-collects the live toolset per iteration instead of fixing it at `Send`). This is an orchestrator-order guarantee: an adapter whose dialect imposes its own deterministic order (the Google adapter re-sorts by name) keeps doing so — Gemini's caching is implicit and the re-sort is that adapter's settled behavior.
- **One validation gate, at `Send`, over the whole universe.** Name uniqueness is enforced across eager `Tools` ∪ MCP tools ∪ every deferred group's tools ∪ the reserved name `load_tools`, and every deferred tool's schema passes the same well-formedness check as an eager `RawTool` (Decision 4) — all at the `Send` boundary, surfacing `ErrInvalidConfig` with no provider call. A deferred tool is a real tool from the start; deferral never delays finding out it was misconfigured. Tool-schema translation warnings (Decision 22) are likewise computed over the whole universe at the same gate.
- **`MCPServers` deferral is explicitly out of scope.** `Conversation.MCPServers` resolution stays eager (Decision 17). A consumer who wants deferred MCP tools lists them with their own client and wraps them into `DeferredToolGroup`s — the primitive composes; folding deferral into agentkit's fail-hard MCP lifecycle (session cache, close semantics) would tangle two features for no consumer that exists. Agent harnesses that consume MCP directly (e.g. Claude Code) already do their own progressive loading.

**Rejected.**

- *A generic `call_tool(name, arguments)` dispatch meta-tool with no dynamic registration* — the model calls real tools through a stringly wrapper, forfeiting provider-native schema enforcement on every actual call; weaker models fumble it, and nothing becomes "really callable".
- *Keyword/BM25 search in the meta-tool* — the catalog is fully visible, so search adds surface without payoff at any pool size a `Conversation` realistically carries; trivially appendable later if ever warranted.
- *Auto-executing a deferred tool on first call (implicit load)* — executes input the model guessed without the schema and rewards skipping discovery; the corrective-error path costs one iteration and yields a schema-correct retry.
- *An unload verb / LRU eviction* — strands `tool_use` history references and doubles the API surface for a bounded, short-lived cost.
- *Injecting the catalog into the system prompt* — AgentKit would mutate consumer prose it currently passes through verbatim; an ownership seam worse than the tool description it already generates.
- *Re-sorting the whole toolset after each load* — a mid-array insertion invalidates the cached prefix of every subsequent round-trip; append-only ordering preserves it.
- *Provider-native deferral (Anthropic's tool-search beta)* — single-provider; this feature must hold uniformly across all four providers, so it lives above the SPI.
- *Deferring `MCPServers` in v1* — see settled choices; recorded rejection, not an accident of scope.

**Verification.**

- R-9RQ8-9G3W — when `DeferredTools` is non-empty, the request tools include a synthesized `load_tools` whose description contains, for every group, the group's `Name`, its `Blurb`, and each deferred tool's bare name — and does **not** contain any deferred tool's own description or input schema.
- R-9SY4-N7UL — when `DeferredTools` is empty or nil, no `load_tools` tool exists in the request and the turn's requests are identical to those of a `Conversation` built without the field.
- R-D5PT-82VU — after the model calls `load_tools` naming deferred tools, the named tools appear in the *next* round-trip's request tools (full description + schema) within the same turn, and a subsequent native call to one of them dispatches to its real `Call`.
- R-D6XP-LUMJ — a successful `load_tools` call's result text carries, for each named tool, its description and its input JSON Schema.
- R-D85L-ZMD8 — a `load_tools` call mixing valid and unknown names loads the valid ones, reports each unknown name as a per-name error in the result text, and is fed back as a normal tool result (the turn continues; not a terminal stream error).
- R-D9DI-DE3X — a tool loaded during one `Send` is still present in the request tools of a later `Send` on the same `Conversation` (monotonic, conversation-scoped; no unload path exists).
- R-DALE-R5UM — the model calling a deferred-but-unloaded tool directly yields `ToolResultBlock{IsError: true}` whose text names `load_tools`; the tool's `Call` is **not** invoked with the guessed input; and the tool is loaded as a side effect, so it appears in the next round-trip's request tools.
- R-DE93-WH2P — a name that is neither eager, loaded, nor deferred still yields the Decision 10 in-band `unknown tool` error result and the turn continues (deferral does not change the truly-unknown path).
- R-DBTB-4XLB — across the round-trips of a turn in which loads occur, the serialized request tool order is the frozen name-sorted base followed by loaded tools in load order; the byte serialization of the pre-existing prefix is identical before and after each load (an implementation that re-sorts the merged set fails this).
- R-DD17-IPC0 — a `Send` whose combined universe (eager ∪ MCP ∪ deferred groups ∪ the reserved name `load_tools`) contains a duplicate name, or whose deferred tool carries an unparseable/invalid JSON Schema, surfaces `ErrInvalidConfig` (matchable via `errors.Is`) through the returned `Stream`, `History` unchanged, no provider call.
- R-DFH0-A8TE — **live substrate:** against a real provider API (Anthropic), a turn whose prompt requires a deferred tool completes end-to-end — the model calls `load_tools`, the grown tools array is accepted by the provider on the following round-trip, the model calls the loaded tool natively, and the turn returns a final answer incorporating the tool's real result. A mocked provider cannot falsify the "provider accepts a tools array that grows between round-trips of one turn" claim; this id names the real API as the substrate.
