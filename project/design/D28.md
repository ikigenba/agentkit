# Decision 28 — `toolkit`: `Read`, `Write`, `Edit` semantics

**Decision.** The three file tools follow the prompts-service schemas verbatim (research §16.1) with one deliberate hardening on `Edit`. All paths pass D27's confinement first.

```go
// package toolkit — input shapes (JSON schema derived via agentkit.NewTool)

type readInput struct {
	FilePath string `json:"file_path"`         // required
	Offset   int    `json:"offset,omitempty"`  // 1-based first line; 0 = start
	Limit    int    `json:"limit,omitempty"`   // max lines; 0 = all remaining
}

type writeInput struct {
	FilePath string `json:"file_path"` // required
	Content  string `json:"content"`   // required
}

type editInput struct {
	FilePath   string `json:"file_path"`  // required
	OldString  string `json:"old_string"` // required, non-empty
	NewString  string `json:"new_string"` // required
	ReplaceAll bool   `json:"replace_all,omitempty"`
}
```

Settled choices:

- **`Read`** returns the file's contents; with `offset`/`limit` it returns the 1-based line slice (offset past EOF yields empty). A missing file is the OS error, surfaced as the tool error — never an empty success.
- **`Read` reads text, and refuses everything else.** The file's content type is sniffed with `net/http.DetectContentType` and anything not detected as text is **rejected with an error naming the detected type**, rather than decoded with `string(content)`. Today a PDF or a PNG returns megabytes of binary garbage as if it were text — a silent corruption that wastes the context window and can wedge an unattended loop. The rejection is **broad, not PDF-and-image-specific**: a zip, an ELF binary, or a database file has no more business being decoded into a string than a scan does, and a narrow rule would fix one instance of the bug while leaving the class of it in place. Detection is by **content, never by extension**, so a `.txt` holding binary is refused and an extensionless UTF-8 file is read normally.
- **The rejection message is generic and names no remedy tool.** It states the path and the detected type and stops there. `Read` cannot see the `ocr` package (a different package it does not import, D31), and whether an OCR tool is even registered depends on harness wiring `toolkit` knows nothing about — so naming one would be a message that is sometimes simply false. Steering a model toward extraction is the OCR tool's *description*'s job, where it is always accurate; this error is only the backstop.
- **`Write`** creates or truncates the file with `content`, creating missing parent directories (`MkdirAll`), and returns a short `wrote <path>` confirmation.
- **`Edit`** replaces `old_string` with `new_string`. With `replace_all` unset it requires `old_string` to match **exactly once**: zero matches is an error, and **more than one match is an error too** (Claude Code semantics, research §16.2) — the prompts service's silent first-occurrence replacement is exactly the wrong-location corruption an unattended loop cannot catch. With `replace_all` set, every occurrence is replaced and the confirmation reports the count. An empty `old_string` is an error.

**Rejected.**
- *`edit` replaces all occurrences unconditionally (agent-repl)* — makes a common single-site edit destructive whenever the snippet is not unique.
- *First-occurrence replacement on ambiguity (prompts service)* — silently edits a location the model may not have meant; fail loudly instead.
- *Default line caps on `Read`* — D27's uniform 30,000-character cap already bounds the result; a second lines-based default adds a knob without adding safety.
- *Detect binaries by file extension* — a scan named `.dat`, an extensionless UTF-8 file, and a `.txt` full of binary all get the wrong answer; the bytes are authoritative.
- *Reject only PDFs and images* — fixes one instance of the corruption bug and leaves the class; every non-text file is equally wrong to decode.
- *Have `Read`'s error name the OCR tool and its arguments* — `toolkit` does not import `ocr` and cannot know whether it is registered in the running harness, so the message would sometimes name tooling the model does not have. The OCR tool's own description carries the steering signal.
- *Return the binary content base64-encoded instead of erroring* — the same context flood in a different encoding; `Read`'s contract is text.

**Verification.**
- R-LXDD-7X8M — `Read` of an existing file with no offset/limit returns its exact contents.
- R-LYL9-LOZB — `Read` with `offset`/`limit` returns exactly the requested 1-based line slice (offset 3 + limit 2 of a 5-line file yields lines 3–4; offset past EOF yields empty).
- R-LZT5-ZGQ0 — `Read` of a missing file returns an error, not an empty success.
- R-M28Y-R07E — `Write` to a path whose parent directories do not exist creates the directories and the file with exactly the given content.
- R-M3GV-4RY3 — `Edit` with a uniquely-matching `old_string` and `replace_all` unset rewrites exactly that occurrence, leaving the rest of the file byte-identical.
- R-M4OR-IJOS — `Edit` whose `old_string` does not occur in the file returns an error and leaves the file unchanged.
- R-M5WN-WBFH — `Edit` whose `old_string` occurs more than once with `replace_all` unset returns an error (the file unchanged) rather than replacing any occurrence.
- R-M74K-A366 — `Edit` with `replace_all` set replaces every occurrence and its confirmation reports the occurrence count.
- R-VGH5-GE0Q — `Read` of a PDF returns an error naming the detected content type (`application/pdf`) and returns **no** file content.
- R-VHP1-U5RF — `Read` of a PNG and of a JPEG each return an error naming the detected image content type, and return no content.
- R-VIWY-7XI4 — `Read` of a UTF-8 text file **with no extension** succeeds and returns its exact contents (detection is content-based, so a missing extension does not cause a refusal).
- R-VK4U-LP8T — `Read` of a file named `*.txt` whose bytes are binary (e.g. a PNG payload) is **rejected**, proving the extension does not override content sniffing.
