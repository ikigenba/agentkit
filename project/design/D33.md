# Decision 33 — Raster normalization: images become one-page PDFs

**Decision.** A raster image is normalized into a minimal single-page PDF before it is sent, so **every** document takes exactly one extraction path. Nothing but the Go standard library is used: `image/jpeg`, `image/png`, and `compress/zlib`.

```go
// package ocr (unexported; exercised through Tool and in-package tests)

// wrapImage embeds a raster image in a minimal one-page PDF.
//   JPEG -> embedded byte-for-byte as a /DCTDecode image XObject (no re-encode)
//   PNG  -> decoded and re-embedded losslessly as raw RGB under /FlateDecode
// Any other detected type is an error.

const wrapDPI = 200.0 // page geometry = pixels / wrapDPI * 72
```

Settled choices:

- **Normalize the input rather than fork the mechanism.** Measured: the `file-parser` plugin is a **no-op for images**. PNG and JPEG sent as `file` blocks returned `annotations: []` with prompt-token counts identical to a no-plugin control, and renaming the upload `page1.pdf` did not change that (research §17.5). Images are handed to the named model's native vision no matter what the plugin says. Accepting that would mean one tool name covering two mechanisms with different output fidelities and different failure modes: PDFs getting real OCR read from `annotations`, images getting a chat model's prose read from `message.content` — precisely the paraphrase path D32 rejects. A raster image *is* a one-page document, so wrapping it keeps the contract one sentence long.
- **Verified to work.** Hand-built one-page PDFs from both a PNG and a JPEG returned real `file` annotations and full OCR text, hitting every ground-truth marker on a known statement.
- **Encoding choice does not affect fidelity, so choose the lossless one.** PNG-lossless and JPEG-passthrough of the same page produced byte-identical OCR text apart from one line break, at a 4× payload-size difference. Since fidelity is unaffected, JPEG is passed through untouched (no generation loss, smallest payload) and PNG is embedded losslessly rather than transcoded to JPEG (no artifacts introduced into text edges, which is where JPEG would hurt if it ever mattered).
- **Stdlib only, honoring D27's dependency rule.** JPEG needs no work at all: its bytes are already a valid `/DCTDecode` stream and embed verbatim. PNG is decoded with `image/png` and re-compressed as raw RGB with `compress/zlib` under `/FlateDecode` (PNG's own IDAT cannot be passed through, because it applies per-scanline filters a PDF `/FlateDecode` image stream does not use). No `gs`, no ImageMagick, no new module — none of which are available in the target sandboxes anyway.
- **Page geometry at 200 dpi.** Page size is `pixels / 200 * 72` points, so a 1698×2200 scan becomes a 611.28×792pt letter page. Physically sensible geometry, and a faithful render round-trip was confirmed.
- **Detection is by content, never by extension**, consistent with D28. PDFs pass through untouched; PNG and JPEG are wrapped; anything else is an error naming the detected type.
- **The PDF writer is small and boring, and that is the point.** Five objects (catalog, pages, page, content stream, image XObject), a correct `xref` table, a trailer. The one thing that must be right is that every `xref` offset points at its object header, since a wrong offset produces a file that some parsers accept and others reject — so it is asserted directly rather than inferred from "the OCR worked".

**Rejected.**
- *Send images as `image_url` to a vision model* — two mechanisms behind one tool name, with the weaker one (model prose, paraphrase risk, no `annotations`) silently applying to every image.
- *Rely on the plugin to handle images* — measured false: `annotations: []` for PNG and JPEG, with or without the plugin.
- *Rename the upload to `.pdf`* — measured false; the filename does not route it.
- *Transcode PNG to JPEG before embedding* — introduces compression artifacts on exactly the sharp text edges OCR reads, for a size win that buys no fidelity.
- *An external tool or module (`gs`, ImageMagick, a PDF library)* — needs operator approval per D27/Conventions, and `convert`/`magick`/`gs` are absent from the target sandbox regardless.
- *Multi-image or multi-page assembly* — no consumer has asked for it; one image is one page.

**Verification.**
- R-UJJV-4KZZ — a JPEG input is embedded **byte-for-byte**: the produced PDF contains the source JPEG's exact bytes as a `/DCTDecode` image XObject stream (no re-encode).
- R-UKRR-ICQO — a PNG input is embedded losslessly under `/FlateDecode`: inflating the produced image stream yields raw RGB whose pixel values equal the source PNG's, pixel for pixel.
- R-ULZN-W4HD — the produced page's `/MediaBox` equals `pixels / 200 * 72` points in both axes (a 1698×2200 source yields 611.28×792).
- R-UOFG-NNYR — the produced PDF's `xref` table is correct: every offset in it points at the byte position of its `N 0 obj` header, and the trailer's `/Size` matches the object count.
- R-UPND-1FPG — an input whose detected content type is neither PDF, PNG, nor JPEG (e.g. GIF, or arbitrary non-image bytes) is rejected with an error naming the detected type, and no request is issued.
