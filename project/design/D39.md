# Decision 39 — Runtime tool-argument validation

**Decision.** Before AgentKit invokes any tool, it validates the model's arguments against that tool's canonical schema (D34) and refuses to dispatch a call whose arguments violate it. This is the enforcement that D22 removed from the wire: strict mode is gone from every provider, so the guarantee that a declared constraint is honored is now AgentKit's own, applied identically on every provider and to every tool source.

The validator lives in root, alongside the schema gate whose subset it enforces, so that one package owns both halves of the contract: `validateToolSchema` decides what a tool may *declare*, `validateToolArguments` decides what the model may *send* against that declaration. Neither adapters nor tool implementations re-decide either question.

```go
package agentkit

// validateToolArguments reports the first violation of schema by args as a
// human-readable reason naming the offending JSON Pointer and the constraint
// it broke. schema is the tool's canonical schema, already known to be inside
// the D34 subset; args is the raw JSON the model emitted for the call.
//
// It is a pure function: it never mutates args, never fills a default, and
// never coerces a value. A nil error means the arguments are dispatchable
// exactly as received.
func validateToolArguments(schema json.RawMessage, args json.RawMessage) error
```

Settled choices:
- **A violation is a corrective tool result, not a turn failure.** The tool is not invoked, and the loop feeds back `ToolResultBlock{IsError: true}` whose content names the violated constraint and its location, so the model can fix the call and continue. This is the shape D10 already established for a tool name the model got wrong (R-VYXN-LXSK): the call cannot be dispatched, tell the model why, keep going. Inventing a second, harder failure mode for the same class of problem would make a recoverable mistake fatal.
- **Runaway correction is already bounded.** A model that keeps sending invalid arguments burns loop iterations and terminates on `MaxToolIterations` with `ErrToolLoopLimit` (D10, R-W05J-ZPJ9). No new guard, no new sentinel, no retry counter of its own.
- **Observability rides the existing log.** A rejection appears in the D15 JSONL log as an ordinary `tool_result` record carrying `IsError` and the reason text (R-PH7W-BVH0), and on `Stream` as the same `ToolResult` any consumer already observes. No new event type and no `Stream` warning: a warning that fires on a recoverable per-turn event is, by D34's own argument, indistinguishable from silence.
- **The whole D34 subset is enforced, minus two deliberate carve-outs.** Enforced: the root-must-be-object rule, `type` including two-branch nullable unions, `required` presence, unknown-property rejection, `enum`, `const`, `properties` and `items` recursively, `anyOf`/`oneOf` as "matches at least one branch", `$ref` resolved against `$defs`, `minLength`, `maxLength`, `minItems`, and `pattern`. Not enforced: `format`, which is accepted and never checked, because the nine allowlisted values are advisory in JSON Schema and nine format parsers rejecting well-typed strings is a bad trade; and `default`, which is never applied, because the validator's job is to refuse, not to author input on the model's behalf.
- **Arguments are never mutated.** The tool receives the bytes the model sent. An omitted optional property stays omitted rather than being filled from `default`, no value is coerced to its declared type, and no key is reordered or dropped. A validator that "helpfully" repairs input would make the tool's observed input differ from the model's stated intent, which is unauditable and hides model errors the log should show.
- **`pattern` compiles with `regexp`.** Go's RE2 engine is exactly the dialect D34 already requires of authored patterns (no lookahead or lookbehind), so the subset and the validator agree by construction rather than by discipline, and a pattern that reached the gate always compiles here.
- **Unknown-property rejection is the closed-object invariant, enforced here rather than on the wire.** D34 forbids authoring `additionalProperties` and D22 has each adapter declare closure in its own dialect; this validator is what makes that declaration true. It is also the constraint that most often matters in practice, since an invented parameter is the commonest way a model's tool call goes wrong.
- **Enforcement is uniform across tool sources, MCP included.** An MCP tool's server-supplied schema is validated exactly as an in-process tool's is, and a violating call is refused before any JSON-RPC request leaves the process. MCP schemas are the external input D34's gate already exists for, and exempting them would leave the tools most likely to carry a wrong schema as the only ones unchecked. Where a server's declared schema is stricter than its handler's actual behavior, the resulting rejection is a true finding about that server, surfaced as a named violation rather than absorbed silently by a lenient handler.
- **No opt-out.** There is no per-tool, per-conversation, or global switch to disable validation. A configurable contract is not a contract, and the failure mode it would exist to work around (a schema that disagrees with its handler) is a defect to fix at the source.
- **No JSON Schema dependency.** The subset is small and closed, so the validator is a few hundred lines of standard library over `encoding/json` and `regexp`. A general JSON Schema library would drag in the full keyword set D34 deliberately excludes and give out-of-subset semantics a back door into the enforcement path, and external modules require explicit operator approval (design Conventions) that this does not need.

**Rejected.**
- *Leaving tool arguments unvalidated, as today* — the status quo only looked tenable while strict mode was doing the work on two of five providers. It was already a hole on Gemini, on `zai`, and on `openrouter`, and D22 makes it a hole everywhere.
- *Failing the turn with `ErrInvalidInput` on a violation* — treats a recoverable model mistake as a caller error. The consumer did nothing wrong and has nothing to fix; the model does, and it is the party able to retry.
- *Validating inside each tool implementation* — pushes identical boilerplate into every tool, cannot be applied to MCP tools at all (their handlers are remote), and makes the guarantee a matter of each author's diligence rather than a property of the library.
- *Validating in each provider adapter* — the arguments are provider-shaped only in transit; by the time the tool loop holds a tool-use block the shape is canonical, and doing it per adapter would mean five implementations that can disagree.
- *Applying `default` when a property is absent* — reads as a convenience and behaves as a silent rewrite of the model's call. The consumer's tool can apply its own defaults with full knowledge of what was actually sent; the library cannot.
- *Coercing a coercible value (a numeric string to a number, say)* — the same silent rewrite with a wider blast radius, and it would let a genuinely confused model appear to be calling the tool correctly.
- *Reporting every violation at once instead of the first* — a larger surface for no gain: the model needs one correction to make progress, and `validateToolSchema` already establishes first-violation reporting as the house convention for schema diagnostics.

**Verification.**
- R-7M3Z-MONZ — a tool call omitting a property listed in `required` is not dispatched (the tool's `Call` is never entered, asserted by a tool that records invocations), and the loop feeds back a `ToolResultBlock{IsError: true}` whose content names the missing property; the turn continues rather than returning an error from `Stream.Err()`.
- R-7NBW-0GEO — a tool call whose argument value has the wrong declared `type` (e.g. a number where the schema declares `"type": "string"`) is rejected with `IsError: true` naming the property and both types, and the tool is not invoked; a validator that accepts a JSON number for a string property fails this.
- R-7OJS-E85D — a tool call carrying a property absent from the schema's `properties` is rejected with `IsError: true` naming the unknown property, enforcing the closed-object invariant that D22's adapters declare on the wire; a validator that ignores unrecognized keys fails this.
- R-7PRO-RZW2 — a value outside a declared string `enum`, and a value unequal to a declared `const`, are each rejected with `IsError: true` naming the constraint and the accepted value(s); a member of the `enum` and a matching `const` each pass and dispatch.
- R-7QZL-5RMR — the length and size constraints are enforced **at their exact boundary**: with `minLength: 3` a two-character string is rejected and a three-character string passes; with `maxLength: 3` a four-character string is rejected and a three-character string passes; with `minItems: 1` an empty array is rejected and a one-element array passes. A validator that only rejects zero-length or empty values, rather than comparing against the declared bound, fails this.
- R-7S7H-JJDG — a string violating a declared `pattern` is rejected with `IsError: true` naming the pattern, and a matching string passes; the pattern is compiled with `regexp` so an RE2-valid pattern that reached the D34 gate always compiles here rather than erroring at validation time.
- R-7TFD-XB45 — under `anyOf`/`oneOf`, a value matching **at least one** branch dispatches and a value matching **no** branch is rejected naming the location; a `$ref` is resolved against `$defs` before its target is applied, so a value violating the referenced subschema is rejected rather than passing unchecked; and a two-branch nullable union accepts both an explicit `null` and a value of the non-null type. A validator that treats an unresolved `$ref` as an unconstrained value fails this.
- R-7UNA-B2UU — `format` is accepted and not checked: a string declared `"format": "email"` whose value is `"not-an-email"` dispatches successfully. And `default` is never applied: an optional property carrying a `default`, omitted by the model, is **absent** from the arguments the tool receives rather than present with the default value. A validator that enforces `format`, or one that fills the default, fails this.
- R-7VV6-OULJ — a valid tool call reaches `Call` with arguments **byte-identical** to what the model emitted, asserted by a tool that captures its raw input: no key reordering, no coercion, no added or removed keys. A validator that round-trips arguments through a map and re-marshals them fails this.
- R-7X33-2MC8 — an MCP tool whose server-supplied schema is violated by the model's arguments is rejected identically to an in-process tool, and **no JSON-RPC `tools/call` request is issued to the server**, asserted against a stub MCP server that records requests; the model receives the same `IsError: true` corrective result. A build that validates only in-process tools fails this by letting the call reach the server.
- R-7YAZ-GE2X — a violation inside a nested object or an array element is caught, and the reason names its location as a JSON Pointer (e.g. `/filters/2/name`) rather than only the top-level property; a validator that checks only the root object's immediate properties fails this.
- R-7ZIV-U5TM — arguments that are not a JSON object (a bare array, a string, `null`, or malformed JSON) are rejected with `IsError: true` naming the received shape, and the tool is not invoked; the turn continues.
