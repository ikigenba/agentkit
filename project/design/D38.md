# Decision 38 — Credentials: absent at construction, named at the call

**Decision.** Every constructor in the module that takes a credential **accepts an absent
credential and constructs successfully**; the failure is deferred to the operation that
needs it and reports **which** credential is missing. No credentialed constructor panics.

The rule exists because credential validity is a property of the **operation**, not of the
constructor. A credential can be present, well-formed, and still unusable by the thing it
was handed to — `openai`'s ChatGPT subscription credential authenticates chat perfectly and
can never serve an embedding, because OAuth tokens are rejected by `api.openai.com/v1/*`
(research §15.2). A constructor cannot decide validity for an operation it does not run, so
it does not try.

Two conditions, deliberately distinct, because they call for different repairs:

| condition | meaning | sentinel |
|---|---|---|
| **absent** | no credential was supplied (empty key, nil token source) | `agentkit.ErrMissingCredential` |
| **unusable** | a real credential the operation cannot use | `agentkit.ErrInvalidConfig` |

```go
// package agentkit — declared beside ErrInvalidConfig, D7's boundary family

// ErrMissingCredential reports that an operation needed a credential that was
// never supplied. Bare sentinel; branch with errors.Is.
var ErrMissingCredential = errors.New("agentkit: missing credential")
```

Settled choices:

- **Construct, then fail at the operation.** A credentialed constructor never inspects the
  credential for presence. The check lives where the credential is used: a provider's
  `RoundTrip`, an embedder's `Embed`, a tool's invocation. The returned error wraps the
  sentinel, so `errors.Is` classifies it and the message identifies it.
- **The message names the operation and the credential's role, in AgentKit's own
  vocabulary.** The library never learns that a key came from `BRAVE_API_KEY` — it reads no
  environment (Conventions) — so it names what it does know: the package or tool that needed
  the credential, and what kind of credential that is. `toolkit.WebSearch: Brave Search API
  key is absent`, `openai: API key is absent`, `openai: a ChatGPT subscription credential
  cannot serve embeddings; an API key is required`.
- **`ErrMissingCredential` is a bare sentinel in D7's boundary-validation family.** No
  payload, matched solely with `errors.Is`, and it does **not** satisfy
  `errors.As(&agentkit.Error{})` — a missing credential is a local setup condition, not a
  provider HTTP failure. It is distinct from `ErrInvalidConfig` so a consumer can tell "you
  forgot the key" from "you passed a nil request", which reusing one sentinel would have
  forced back into message string-matching.
- **The unusable case keeps `ErrInvalidConfig`.** Something *was* configured and the
  configuration is wrong for the operation. Reporting a missing credential there would state
  a falsehood: a credential was supplied.
- **Credentials are typed everywhere, including in `toolkit`.** D5's per-package closed
  credential set is the module-wide rule, and `toolkit` now follows it:
  `toolkit.WebSearch(key BraveAPIKey)` with `type BraveAPIKey string`, replacing the bare
  `string` that let a root path or a query be passed where a key belongs. Typing is enforced
  by the compiler, so it carries no Verification id of its own — the suite building is the
  proof.
- **Absence never changes a tool set's shape.** A consumer wiring a credentialed tool whose
  credential is absent still gets the tool, so its agent's tool set is fixed and
  environment-independent. A harness whose tool set changed with whichever keys happened to
  be set would misrepresent what it was handed.
- **Scope: credentials only.** This Decision governs credential absence and credential
  usability, nothing else. The module's other panics are a different species — static
  programmer errors on sealed internal invariants, unreachable for any correct caller — and
  are **untouched**: `NewTool`'s panic on an unmappable input struct (D4) and each adapter's
  block-translation panic on an unknown block type (D9) both stand, with their reasoning
  intact.
- **MCP is excluded, deliberately.** MCP servers authenticate with free-form `Headers` on a
  server config (D17), not a typed credential. There is nothing named to detect as absent —
  an omitted auth header is indistinguishable from a server that needs none — and when it
  matters the server answers `401`, which D7 already maps to `ErrAuthentication`. This
  convention needs a typed credential to name; MCP has none by design, and giving it one
  would be a change to D17, not an application of this rule.

**Rejected.**
- *Panic at construction* — the prior choice in D36 ("a misconfiguration surfaces at startup,
  never as a mid-conversation auth error") and, independently, in D19 ("rejected loudly at
  construction"). Re-argued here and lost on two counts. It is unavailable to a consumer that
  must wire a fixed tool set before knowing which credentials are present, whose only recourse
  against a panicking constructor is to pass a placeholder string — which converts a
  self-describing failure into a bare provider `4xx` and pushes a workaround into every
  consumer. And it asserts at construction a validity only the operation can judge: the
  panic could not have caught `Subscription` + embeddings without hard-coding one operation's
  rule into a constructor shared with another.
- *Startup failure or a conditional tool set on an absent credential* — the same defect
  without the crash: the agent's capabilities become a function of the deployment
  environment, so the same code offers different tools on different machines.
- *One sentinel for both conditions* — collapses "set the key" and "this credential can't do
  this" into one branch, leaving the distinction only in prose and inviting exactly the
  message string-matching D7 forbids.
- *Naming the external variable (`BRAVE_API_KEY`) in the error* — requires the consumer to
  pass a label at construction, carrying knowledge the consumer already has, to improve a
  message that consumer reads in its own codebase. The catalog cannot supply it either:
  D26 is consumer-facing only and nothing in the request path may import it.
- *Narrowing `openai.NewEmbedder` to `APIKey` so the compiler rejects a subscription
  credential* — makes the wrong-kind case a compile error, but splits the credential union a
  consumer selects at runtime and forces that consumer to write the type assertion this
  module just deleted. The union is the right parameter; the operation is the right judge.

**Verification.**
- R-UF7D-AWAA — `ErrMissingCredential` is a bare sentinel: an error wrapping it satisfies `errors.Is(err, agentkit.ErrMissingCredential)`, does **not** satisfy `errors.Is(err, agentkit.ErrInvalidConfig)`, and does **not** satisfy `errors.As(err, &agentkit.Error{})`; a plain `ErrInvalidConfig` likewise does not match `ErrMissingCredential`. A single sentinel serving both conditions fails this.
- R-UGF9-OO0Z — `toolkit.WebSearch(BraveAPIKey(""))` returns a tool without panicking (asserted via `recover`), and invoking that tool returns an error wrapping `ErrMissingCredential` whose message names both `WebSearch` and the Brave Search API key, with **no** HTTP request issued (recorded request count = 0 against an `httptest` backend). A construction-time panic or a request carrying an empty `X-Subscription-Token` fails this.
- R-UHN6-2FRO — `ocr.New(ocr.APIKey(""))` returns a client without panicking, and a tool call against it fails with an error wrapping `ErrMissingCredential` naming the OpenRouter API key and issues no HTTP request; a client with a real key but an empty base URL fails instead with `ErrInvalidConfig` and a message naming the base URL. The two conditions produce **different** sentinels and different messages — one shared "invalid configuration" error fails this.
- R-UIV2-G7ID — `openai.New(openai.APIKey(""))` and `openai.New(openai.Subscription(nil))` each construct without panicking, and a `Send` against either surfaces through `Stream.Err()` an error wrapping `ErrMissingCredential` naming the API key and the ChatGPT subscription token source respectively — two distinct messages — with no HTTP request issued. A nil `*Provider` or a nil `*Request` still surfaces `ErrInvalidConfig`, unchanged.
- R-ULAV-7QZR — `openai.NewEmbedder(openai.APIKey(""))` constructs without panicking and its `Embed` fails with an error wrapping `ErrMissingCredential` naming the API key; `openai.NewEmbedder(openai.Subscription(ts))` with a live token source also constructs without panicking, and its `Embed` fails with an error wrapping `ErrInvalidConfig` — **not** `ErrMissingCredential` — whose message states that a ChatGPT subscription cannot serve embeddings. Neither issues an HTTP request.
- R-UMIR-LIQG — `google.New(google.APIKey(""))` constructs without panicking and a `Send` against it surfaces `ErrMissingCredential` naming the Google API key through `Stream.Err()`; `google.NewEmbedder(google.APIKey(""))` constructs without panicking and its `Embed` fails wrapping the same sentinel. Neither issues an HTTP request.
- R-UNQN-ZAH5 — for each of `anthropic`, `zai`, and `openrouter`, `New(APIKey(""))` constructs without panicking and a `Send` against it surfaces through `Stream.Err()` an error wrapping `ErrMissingCredential` whose message names that package and its API key, with no HTTP request issued (table-driven across all three; a test covering only one package does not satisfy this id).
