# Decision 35 — The assembled message is transport-shape-independent

**Decision.** An adapter's assembled `Message` is a function of *what the model
said*, never of *how the provider's transport chopped it up*. Two responses
carrying identical content assemble to identical `[]Block` regardless of how
many SSE frames delivered them. This was an unwritten assumption that three of
four adapters happened to satisfy; it is now a stated invariant, enforced in one
place, and proven by tests that send real multi-frame bodies.

The invariant, stated exactly:

> An assembled `Message` never contains two **adjacent** `TextBlock`s. Text
> merges only across an uninterrupted run; a `ToolUseBlock`, `ToolResultBlock`,
> or `ReasoningBlock` between two text blocks breaks the run and both survive,
> in order.

Adjacency is the whole rule. Merging *all* text in a message would destroy real
model structure (that some text preceded a tool call and some followed it) and
would corrupt the positional `ReasoningBlock.BoundToID` binding of D3
(R-IPGC-I69W), which Gemini defines by part order.

**Two seams, deliberately both.**

*1. Central enforcement at the SPI boundary.* Every adapter hands its result to
`agentkit.NewRoundTrip` (root `orchestration.go`), the single constructor for
the type; it already clones the `Message` on the way in. Normalization happens
there, so the invariant holds for every current and future adapter without each
one remembering it:

```go
// NewRoundTrip normalizes the assembled message before storing it: adjacent
// TextBlocks are merged into one (D35). Text is joined verbatim — no
// separator, no trimming — because the fragments are transport slices of one
// string, not independent values.
func NewRoundTrip(message Message, finish FinishReason, usage Usage, warnings []Warning, err error, reportedCost Cost, reportedCostOK bool) *RoundTrip

// mergeAdjacentText returns blocks with each maximal run of adjacent
// TextBlocks replaced by a single TextBlock holding their concatenation.
// Non-text blocks pass through untouched, in order. Empty-text blocks are
// dropped only when merging leaves an empty run.
func mergeAdjacentText(blocks []Block) []Block
```

*2. The Google adapter stops creating the damage.* Central merging repairs
fragmented text, but it cannot repair everything per-frame parsing breaks, so
Google is fixed at the source as well. `google.parseResponse` currently calls
`parseParts` **once per decoded SSE frame** and appends each result. It instead
concatenates every frame's `candidate.Content.Parts` into one slice and parses
that slice **once**, making a streamed body produce byte-identical output to a
unary body of the same content:

```go
// parseResponse decodes the SSE body into frames, concatenates every frame's
// parts into a single slice, and parses that slice once. Per-frame parsing is
// what leaked transport shape into Blocks; a single parse over the whole
// stream cannot. Finish reason and usage still fold across frames.
func parseResponse(contentType string, raw []byte) (agentkit.Message, agentkit.FinishReason, agentkit.Usage, error)
```

This is not a cosmetic refactor. `parseParts` ends with `flushPending("")`,
which binds any pending `thoughtSignature` to nothing. Called per frame, that
flush fires at **every frame boundary**, so a signature arriving in frame N can
never bind to the `functionCall` arriving in frame N+1: the `ReasoningBlock`
lands with `BoundToID == ""` and the replay chain for that call is silently
lost. Merging text afterward does not touch this. Parsing once does, because the
signature and the call are then adjacent entries in a single parts slice, which
is exactly the case `parseParts` already handles correctly. Within-frame text
splitting (`parts: [{"text":"one"},{"text":"two"}]`, which Gemini also emits) is
covered by the same central merge.

**Why the existing tests missed all of it.** `google_test.go`'s `writeSSE`
helper takes a single `data string` and writes one frame; all twelve call sites
pass one frame. No Google test has ever sent a multi-frame body, so the entire
class of frame-boundary defect was structurally unreachable by the suite, and
`R-IPGC-I69W` is currently proven only by a fixture that packs signature and
call into one frame — a shape the live API does not produce. The helper must
become variadic (`writeSSE(t, w, data ...string)`) so the real wire shape is
expressible; that change alone is what makes the rest falsifiable.

**Rejected.**
- *Fix only the Google adapter.* Restores the coincidence without removing the
  condition that produced it: the invariant stays unwritten and untested, and
  the next adapter or wire-format change reintroduces it. Central enforcement
  costs one function.
- *Fix only centrally, leaving Google's per-frame parse.* Merging text hides the
  visible symptom while the `BoundToID` binding stays broken, which is the worse
  half of the defect and the one no consumer would notice until a replay fails.
- *Merge all `TextBlock`s in a message into one.* Destroys real structure and
  breaks D3's positional reasoning binding. Adjacency is the correct boundary.
- *Coalesce in the consumer instead (a `Message.Text()` accessor).* Leaves
  `History` holding transport fragments, which are then replayed to the provider
  as N text parts on the next tool-loop turn — a different request body for a
  pure transport accident. The corruption is provider-visible, not just
  display-visible, so a consumer-side accessor cannot fix it.
- *Expose the frames to consumers as deltas.* A separate, much larger redesign
  (every adapter does `io.ReadAll` before parsing; deltas mean holding the body
  open across consumer iteration and reopening D10's early-break atomicity). It
  would not remove one line of this work, since `History` still needs a
  consolidated message either way. Out of scope here, not foreclosed.
- *Merging with a separator, or trimming fragments.* The fragments are slices of
  one string and split mid-word (`"I have"` + `" access to"`); anything but
  verbatim concatenation corrupts the text.

**Verification.**
- R-QUWY-MLCD — a Google SSE body delivering one reply across **multiple
  frames**, each frame's `parts` carrying a slice of the text (splitting
  mid-word, as the live API does), assembles to a `Message` containing exactly
  **one** `TextBlock` whose `Text` equals the verbatim concatenation of every
  fragment, with no separator inserted and nothing trimmed. The identical
  content delivered as a single frame assembles to a byte-identical `Message`.
- R-QW4V-0D32 — a Google SSE **single** frame whose `parts` slice carries two
  adjacent `text` parts assembles to one `TextBlock` holding both, proving the
  merge covers within-frame splitting and not only cross-frame splitting.
- R-QXCR-E4TR — a Google SSE body whose `thoughtSignature` part arrives in one
  frame and whose `functionCall` arrives in a **later** frame assembles a
  `ReasoningBlock` whose `BoundToID` equals that `ToolUseBlock`'s minted `ID`,
  non-empty — the cross-frame case the per-frame `flushPending("")` left unbound
  and that no text merging repairs. Asserted on a multi-frame body; the existing
  single-frame `R-IPGC-I69W` fixture does not exercise it.
- R-QYKN-RWKG — a Google SSE body delivering text, then a `functionCall`, then
  more text, across separate frames, assembles to exactly three blocks in that
  order (`TextBlock`, `ToolUseBlock`, `TextBlock`) — the two text runs are
  **not** merged across the intervening tool call, and the second text block is
  not hoisted ahead of it.
- R-QZSK-5OB5 — `NewRoundTrip` merges adjacent `TextBlock`s in the `Message` it
  is handed, for **every** adapter and not just Google: an assembled `Message`
  built with adjacent text blocks emerges from `RoundTrip.Message()` with them
  joined verbatim into one, while a `Message` whose text blocks are separated by
  a `ToolUseBlock` or a `ReasoningBlock` emerges with both text blocks intact
  and in order. Asserted directly against the root constructor, so the invariant
  is proven independently of any provider's parse.
- R-R10G-JG1U — a **live** Gemini call (integration-tagged, real credentials)
  whose prompt elicits a multi-sentence reply returns a `Message` carrying
  exactly one `TextBlock` whose text is the complete answer. This id exists
  because the claim is about the real provider's transport behavior: a fixture
  proves the adapter handles the frame shape we believe Gemini sends, and only a
  live call proves that belief is still true. The assertion is on the returned
  block count and non-empty text of a completed call, not on any configured
  value.
