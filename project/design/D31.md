# Decision 31 — The `ocr` package: the document-text tool, its cache, and its transcript

**Decision.** A new leaf subpackage `github.com/ikigenba/agentkit/ocr` (package `ocr`) provides one `agentkit.Tool` that turns a scanned PDF or raster image into text. It is deliberately **not** part of `toolkit`: every `toolkit` tool is free, offline, instant, and deterministic, and this one costs money per page, needs a credential, takes seconds, and reaches the network. Folding it in would make `toolkit`'s confinement promise misleading — a file tool that rejects `../secrets` while uploading a file *inside* the root to a third party is a guarantee that no longer means what its documentation says.

```go
// package ocr

// Client is the document-parsing backend (D32). The consumer constructs it
// with ocr.New and passes it in; Tool never builds one, never reads an
// environment variable, and never touches a credential store (Conventions:
// explicit credentials).
//
//	backend := ocr.New(ocr.APIKey(key))          // or …, ocr.WithModel("…"))

// Tool returns the OCR tool, declared to the model as "OCR".
//
//	root     — source paths resolve here and may not escape it (D27 confinement);
//	           the readable transcript is written here, under root/ocr/
//	cacheDir — the durable cache of raw provider responses; required, never "".
//	           May sit anywhere, inside root or outside it.
func Tool(root, cacheDir string, backend *Client) agentkit.Tool

type ocrInput struct {
	FilePath string `json:"file_path"` // required; the only field
}

const maxPreviewCharacters = 30_000
```

The two artifacts live in two places, keyed alike:

```
<cacheDir>/<stem>-<hash8>.json    raw provider response; durable, written on a miss
<root>/ocr/<stem>-<hash8>.md      derived transcript; written on every call
```

Settled choices:

- **The expensive artifact is cached; the cheap one is derived.** A provider response costs money per page to obtain, so it is what the cache holds. `Transcript` (D32) is a pure function of those bytes, so its output is free to recompute and is never stored durably. This is what lets the two artifacts live in different directories, which is the point: `cacheDir` must outlive any single agent run to be a cache at all, while the transcript must sit inside `root` or the agent cannot open it. Writing both to one directory cannot satisfy both, because the two requirements pull in opposite directions. Deriving instead of caching dissolves the conflict rather than trading one requirement against the other.
- **The transcript is written inside `root`, so it is reachable by construction.** The agent's file tools are confined to `root` (D27), so a path outside it is not merely inconvenient, it cannot be opened at all: `Read`, `Write`, `Edit`, `Glob`, and `Grep` all reject it. Returning a path under `cacheDir` therefore hands the model a path it cannot use whenever the consumer puts the cache somewhere durable, which is exactly where a cache belongs. Placing the transcript under `root` removes the failure instead of documenting it.
- **`root/ocr/`, a named subdirectory, not `root` itself.** The working directory is also the agent's own workspace, and machine-generated transcripts interleaved with its output make "what did this run produce" unanswerable. A visible (not dot-prefixed) `ocr/` keeps them together, keeps them out of the agent's own `*.md` globs at the top level, and stays discoverable by ordinary listing rather than only through the returned path.
- **The model chooses a document, never a destination.** The input schema carries `file_path` and nothing else. The wiring service names `cacheDir` once at construction, because where files land is a deployment fact it owns and the model has no legitimate opinion about. This is not tidiness: a cache is only a cache if the same input maps to the same output path, and a model-chosen destination re-OCRs the same document at three paths across three turns. It also removes a second confinable path from the model's reach.
- **`cacheDir` is required.** An empty value meaning "don't cache, return inline" would create a second result shape and a second failure mode. One contract. It may equal `root`, which makes the cache run-scoped; that is a deployment choice, not a different code path.
- **The cache entry is a single file**, named `<source-stem>-<hash8>.json` where `hash8` is the first 8 hex chars of the SHA-256 of the **source file's bytes**. Content-addressed, so an edited source misses correctly and a stale transcript for changed content is impossible; stem-prefixed, so a human scanning the directory can see what is in it. The same bytes under two different filenames are extracted twice, a rare case traded knowingly for legibility. One file per location means an ordinary temp-file-plus-rename is atomic enough; nothing needs to assemble a directory and rename it into place.
- **`transcript`, not `.txt`.** The engine returns Markdown, `##` headings and pipe tables (D32), so the `.md` extension states what the file is.
- **The transcript is rewritten on every call, hit or miss.** One code path serves both, and the file repairs itself: an agent that deletes, truncates, or edits it gets the derived text back by calling `OCR` again, with no provider request. The cost is that an agent's own edits to that file are silently discarded on the next call for the same document. That is accepted: the file is derived output owned by the tool, and an agent that wants to annotate copies it first. It also means a fix to `Transcript` reaches every document on its next call, with no cache walk and no re-extraction.
- **A cache entry that fails to derive is an error, not a re-extraction.** Every cached response passed `Transcript` at write time, so a later failure means the bytes changed on disk or `Transcript` itself changed to reject what it once accepted. Both are faults worth surfacing (`principles`: crash over silent corruption), and silently re-extracting would convert a deriver regression into a fresh provider charge for every affected document with no visible symptom. The tool errors before reaching the network, so a corrupt entry costs nothing and is cleared by deleting the file.
- **The tool returns a preview plus the transcript path**, always in that one shape, never branching on size. Always-write means the contract has one form and the common small document still completes in a single call because its preview contains the whole text. The preview is a **verbatim prefix** of the transcript — never reworded, never summarized — capped at **30,000 characters** (matching D27's cap, so an agent learns one ceiling, a deliberate duplication of a value rather than shared code across packages) and cut at the **last page boundary that fits**. Characters set the ceiling because only a character count bounds context; page boundaries choose the cut so a Markdown table is never severed mid-row. A single page larger than the cap falls back to the last line boundary, so one oversized page still cannot breach the bound. Both outcomes are marked explicitly — the complete case says so, the truncated case names shown pages, shown characters, and totals — so nothing is ever silently cut.
- **The cached response is never named to the model.** It is an operator and debugging artifact: one enormous line containing base64 image payloads, on which `Read` is a context bomb and `Grep` returns 25,000-character lines. It also sits outside `root` in any real deployment, so no confined tool could open it anyway. The model's path to anything past the preview is `Read`/`Grep` on the transcript.
- **Nothing is written or cached on failure.** A failed extraction (D32's error cases) leaves both locations untouched, so a transient failure is never frozen into a permanent empty result that every later call happily serves.
- **No pre-flight size guard.** Measured behavior forbids one: a 23.3MB / 114-page PDF succeeded while a 24.1MB / 385-page PDF was rejected, because the provider's 30MB ceiling applies to the *images extracted from inside* the document, not the file (research §17.4). A guard on `stat` size would reject working files and admit failing ones. The tool sends the document and handles the failure well.
- **Source paths are confined to `root`** by the same rule as D27's file tools, symlink-resolution included. Confinement is checked before any network call, so a rejected path never costs money.
- **The backend is a caller-supplied value, not an interface — yet.** Auth-mode routing is a per-capability judgment (product Scope), so a second backend on subscription auth is a named future, not speculation. But the two candidate shapes differ materially — OpenRouter returns Markdown only, while a direct Mistral OCR API also returns bounding boxes, typed blocks, and confidence scores (research §17.6) — so an interface minted against the single implementation in hand would encode its limitations. The *parameter position* is reserved instead: introducing `ocr.Extractor` later and widening the parameter to it is source-compatible, since `*Client` already satisfies it and every call site compiles unchanged. The irreversible mistake is not the missing interface; it is `Tool` constructing its own backend or reading a key, which is prohibited above.

**Rejected.**
- *Put the tool in `toolkit`* — destroys the one property that makes `toolkit` describable (free, offline, instant, deterministic, confined) and turns its confinement guarantee into a false statement, since the path is confined but the contents are uploaded.
- *An SPI in the root package with the tool in `toolkit` and the backend in `openrouter`* — smears one capability across three packages, puts a document-extraction concept into the provider-agnostic core where it is not universal, and creates a sub-package→sub-package edge that would drag the OpenRouter client into every `toolkit` consumer, against D9's dependency isolation.
- *Both artifacts in `cacheDir`, the tool returning a `cacheDir` path* — the shape this Decision replaces. It forces the consumer to choose between a cache that survives the run and a transcript the agent can open, because a durable `cacheDir` sits outside `root` and an in-`root` one is destroyed with the sandbox. Neither choice is acceptable, and no value of `cacheDir` avoids the fork.
- *Require `cacheDir == root`, making the cache run-scoped* — works with no code change and keeps one directory, but a fresh sandbox per run means the cache never survives, so every run re-pays the provider for documents already extracted. It also drops the raw response into the agent's deliverables folder.
- *A consumer-side wrapper that copies the transcript into `root`* — makes every consumer absorb an upstream API flaw, and the second consumer writes the same wrapper again.
- *Reaching the transcript through the unconfined `Bash` tool* — the confinement story tells agents every path resolves inside the root, and D27 keeps `Bash` unconfined as an acknowledged hole, not a supported route around the file tools.
- *Return the text inline with no file* — caps the model's reach at 30,000 characters; a 114-page document produced ~920,000 characters of text, roughly 30× the cap.
- *Return only the cached response path* — the model then needs `jq` through the unconfined `Bash`, and the wire-format knowledge that D32 isolates in one tested function would move into the model's head, where nothing covers it.
- *Page bounds (`offset`/`limit`) on the OCR tool* — duplicates paging `Read` already does and searching `Grep` already does, and adds a second cap. Conversion is this tool's job; presentation is `Read`'s.
- *Model-supplied output path* — breaks cache determinism and adds a confinable path for no gain.
- *A `force` flag on the input schema, to bust the cache* — the key is content-addressed on the source bytes, so the stale-cache case it would solve cannot arise: change the document and the key changes. The only entry it could clear is a corrupt one, which is an operator fault with an operator fix (`rm` the file). Against that it adds a second field to a schema deliberately held at one, hands the model a spend lever on a tool where one call is real money, and creates a second request shape.
- *Widening `hash8` past 8 hex characters* — a 32-bit prefix under a filename stem needs on the order of 9,000 same-stem documents before a 1% collision chance, which no realistic corpus reaches. The existing legibility trade stands.
- *Keeping the cache entry as a directory* — it existed only so `response.json` and `transcript.md` became visible together atomically. With one file left in it, the directory is a container holding a single item and the rename that made it atomic is no longer needed.
- *Eviction, TTL, or a size limit on the cache* — a policy engine before any consumer has asked for one; the service owns the directory and can delete it. D27 already rejected this shape of speculative configuration once.
- *Writing the extracted images as separate files* — they are capped at 8 per document regardless of length (research §17.3), so writing them would imply a completeness the data does not have. They remain preserved verbatim inside the cached response.

**Verification.**
- R-V1UC-V54E — `Tool` returns a tool whose declared name is `OCR` and whose input schema has exactly one property, `file_path`, and no destination/output-path or cache-control field.
- R-V329-8WV3 — a `file_path` resolving outside `root` (via `../` or via a symlink inside the root) is rejected with an error, and **no HTTP request is issued** (asserted against an `httptest` backend that records request count = 0).
- R-V4A5-MOLS — a successful extraction writes exactly `<cacheDir>/<stem>-<hash8>.json` holding the raw response body byte-for-byte, and `<root>/ocr/<stem>-<hash8>.md` holding the derived transcript, where `hash8` is the first 8 hex characters of the SHA-256 of the source bytes.
- R-UTL6-Q86Y — with `cacheDir` and `root` as **disjoint** directories (neither containing the other), the path the tool returns resolves inside `root`, and no `.md` file exists anywhere under `cacheDir`. This is the property the split layout exists to guarantee; a test whose `cacheDir` sits inside `root` cannot falsify it and does not satisfy this id.
- R-V6PY-E836 — editing the source file's bytes (same filename) produces a **different** `<stem>-<hash8>` key and issues a new HTTP request; the previous cache file is left intact.
- R-V7XU-RZTV — a second call on an unchanged source issues **no** HTTP request (recorded request count stays 1) and returns the same transcript path.
- R-V95R-5RKK — with the transcript deleted but the cached response present, the next call rewrites the transcript byte-identically and issues **no** HTTP request.
- R-UW0Z-HROC — with the transcript present but its contents modified, the next call overwrites it with the derived text and issues **no** HTTP request; the agent's edit is not preserved.
- R-UX8V-VJF1 — a cached `<cacheDir>/<stem>-<hash8>.json` whose bytes `Transcript` rejects causes the call to return an error, issue **no** HTTP request (recorded request count = 0), and leave the cache file in place rather than deleting or overwriting it.
- R-VADN-JJB9 — a transcript at or under 30,000 characters is returned in full, with a marker stating the transcript is complete.
- R-VBLJ-XB1Y — a transcript exceeding 30,000 characters is returned cut at the **last page boundary that fits**: the returned preview is a verbatim prefix of the transcript file, is ≤ 30,000 characters, ends at a page boundary, and carries a marker naming shown pages, shown characters, and total characters.
- R-VCTG-B2SN — when page 1 alone exceeds 30,000 characters the preview falls back to the last line boundary and is still ≤ 30,000 characters (a single oversized page cannot breach the bound).
- R-VE1C-OUJC — a failed extraction (D32 error cases) writes nothing in **either** location: no file exists under `cacheDir` and none under `<root>/ocr/` afterwards, and a subsequent successful call performs a fresh HTTP request.
- R-VF99-2MA1 — the tool result names the `<root>/ocr/<stem>-<hash8>.md` path and never mentions the cached response file or `cacheDir`.
