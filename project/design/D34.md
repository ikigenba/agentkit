# Decision 34 — The canonical tool-schema subset, owned by root

**Decision.** AgentKit defines **one canonical subset of JSON Schema that every tool's input schema must fit**, owned by the root `agentkit` package, enforced identically for every tool from every source, and independent of which provider a conversation is configured with. A schema outside the subset is `ErrInvalidConfig` at the `Send` boundary. Nothing is dropped, nothing is warned about, and no schema construct ever reaches a provider that cannot express it.

The subset is **derived, not chosen**: it is exactly the set of constructs with a faithful rendering in *every* provider dialect AgentKit supports (research §18). Membership is a fact about the measured dialects, not a taste judgment, and it widens automatically when a provider's dialect does.

Root owns it because root is the only package that can. A `Conversation` holds exactly one `Provider`, and provider packages import root (never the reverse), so root cannot reach a dialect description belonging to a provider that is not configured. Enforcing "renderable by all providers" is therefore only possible from root. This is a deliberate reversal of the superseded model in which root held no schema knowledge and each provider declared its own narrowness through an optional capability interface; that model can only ever enforce against the configured provider, which would let a tool pass on Anthropic and fail on Gemini.

```go
package agentkit

// Constructs permitted in a tool input schema. Derived from research §18: a
// construct is a member iff every supported provider dialect can render it
// faithfully. Root owns this because root cannot import provider packages and a
// Conversation holds only one Provider, so no per-provider description can
// answer "renderable everywhere".
//
// validateToolSchema reports the first violation as a human-readable reason
// naming the offending JSON Pointer and construct. It is the sole authority on
// membership; adapters render, they never re-decide.
func validateToolSchema(schema json.RawMessage) error
```

**The subset.** The root of every tool schema must be `"type": "object"` — OpenAI rejects any other root shape unconditionally, strict or not (research §18.2), and Gemini's `parameters` occupies the same object-schema position — so a root `anyOf` or a non-object root `type` is out of subset regardless of the constructs inside it. Within that root, permitted: `type` (single value), `description`, `title`, `properties`, `required`, `items`, `enum` (string values only), `const` (string value only), `anyOf`, `oneOf` (rendered as `anyOf`), `$ref`/`$defs` (inlined at render time), `minLength`, `maxLength`, `pattern` (RE2-safe: no lookahead/lookbehind), `minItems` (values 0 or 1 only), `format` (nine measured values only: `date-time`, `date`, `time`, `duration`, `email`, `hostname`, `ipv4`, `ipv6`, `uuid`), `default`, and a two-branch nullable union.

Excluded, each because at least one dialect cannot express it: `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `multipleOf`, `maxItems`, `uniqueItems` (Anthropic strict rejects); `allOf`, `not`, `if`/`then`/`else` (OpenAI strict rejects `allOf`, all three reject `not`); `patternProperties` (Anthropic strict rejects); recursive `$ref` (Anthropic and Gemini reject); non-string `enum` or `const` values (Gemini's `enum` is a protobuf `string[]` — a numeric enum has no representation, and `const` renders there as a one-element `enum`, research §18.1); `additionalProperties` in any authored form; any `format` value outside the nine — Anthropic strict allowlists exactly ten formats (the nine plus `uri`) and 400s on every other value, while OpenAI strict rejects `uri`, so the two allowlists overlap without either containing the other and only the measured intersection survives (research §18.2, §18.3); `propertyNames`, `prefixItems`, `contains`, `dependentSchemas`, `unevaluated*`, `$schema`, `$id`, `$comment`.

Settled choices:
- **`additionalProperties` is adapter-owned and never authored.** Anthropic and OpenAI accept the keyword and Gemini 400s on it (research §18.1, §18.2, §18.3), so no authored value could be correct for all three. A tool schema containing it is rejected; each adapter injects or omits it per its own dialect (D22). "Closed object" is the invariant meaning — Anthropic and OpenAI spell it with the keyword, Gemini by omission, since Gemini only ever generates declared properties — and D39's runtime validator is what enforces that meaning, by rejecting a tool call carrying a property the schema does not declare.
- **Rejection is whole-toolset, not per-tool.** One offending tool fails the entire `Send` with `ErrInvalidConfig`, `History` unchanged and no provider call — matching the existing duplicate-name and malformed-schema gates rather than inventing a second, softer failure mode for the same class of problem.
- **The gate replaces the parseability check.** The superseded `validJSONSchema` accepted anything that unmarshalled to a `bool` or an object, so `{"type":"nonsense"}` and an unresolvable `$ref` both passed. Subset validation subsumes and strictly strengthens it.
- **Error text names the construct and its location**, so a rejected tool is diagnosable without re-reading this document.
- **Membership is enforced by AgentKit, not borrowed from a provider's strict mode, and the list does not widen because strict is gone.** D22 removed the strict flag from every provider's wire, so no provider now validates a tool schema at all, and D39's runtime validator is what makes the subset's constraints real. That changes who enforces the subset; it does not change what is in it. Eight constructs are excluded here because Anthropic strict rejects them, and research §18.4 establishes that a non-strict provider accepting a keyword neither validates nor honors it — so a strict rejection is read as evidence the provider does not understand the construct, and the exclusion stands independently of whether the flag is on the wire. Widening the subset on the grounds that AgentKit enforces it anyway is a coherent argument and a different Decision: it would require the Google renderer to drop constructs Gemini's parser cannot carry, which is the silent weakening this Decision exists to forbid, and it needs its own measurement before it can be made.
- **The gate is the boundary validator, not the first line of defense for reflector-built tools.** A tool from `NewTool` fails early: the constructor panics on an input struct the reflector cannot map into the subset (D4), so such a schema never reaches the gate from that source. The gate's irreplaceable job is external input — MCP server schemas, which never pass through `NewTool` — and it validates every tool from every source identically as the backstop, so a schema that bypasses construction (or a future defect in the reflector) is still caught before any provider call.

**Rejected.**
- *Warning on an unrenderable construct instead of erroring* — the superseded model. Research §18.4 removes its premise: a non-strict provider that accepts a keyword does not honor it, so "warn and proceed" ships a silently weakened contract and the observed failure is wrong tool arguments at runtime, not graceful degradation. A warning emitted on every turn is indistinguishable from silence.
- *Per-provider subsets, enforced only against the configured provider* — strictly more expressive, and still loud, but a tool would pass on one provider and fail on another. Uniformity across providers is the product promise; expressiveness is not.
- *Providers declaring their own dialects through a capability interface* — structurally impossible to use for uniform enforcement, since root cannot import provider packages and holds only the configured one.
- *Dropping unrenderable constructs mechanically per provider* — indistinguishable from the silent weakening this Decision exists to remove.
- *Gemini's `parametersJsonSchema` field to widen the subset* — it accepts full JSON Schema, including invented keys, by dropping unsupported keywords silently (research §18.1). It trades our visible failure for the provider's invisible one.

**Verification.**
- R-XLTO-JMIA — a `Send` whose tool set contains a schema using a construct outside the subset (e.g. `minimum`, `not`, `allOf`, `patternProperties`, or an authored `additionalProperties`) surfaces `ErrInvalidConfig` (matchable via `errors.Is`) through the returned `Stream`, leaves `History` unchanged, and issues **no** provider call; the error text names the offending construct and its location in the schema. A schema using only subset constructs passes the gate.
- R-XRX6-GH7R — the identical out-of-subset schema is rejected with `ErrInvalidConfig` under **every** provider, including one whose own dialect would accept the construct (e.g. `minimum` under OpenAI, `allOf` under Anthropic), proving enforcement is provider-independent; a build that consults the configured provider's dialect and admits the construct fails this.
- R-XN1K-XE8Z — a tool schema carrying a schema-valued `additionalProperties` (the shape a Go map reflects to), supplied from a source that bypasses `NewTool` (an MCP tool or a test-only helper), is rejected at the `Send` gate with `ErrInvalidConfig` naming that construct, rather than being sent with the map's value schema silently lost.
- R-XO9H-B5ZO — a tool schema carrying a recursive `$ref`, supplied from a source that bypasses `NewTool`, is rejected at the `Send` gate with `ErrInvalidConfig` naming the recursive reference; no provider call is issued and no dangling `$ref` is emitted.
- R-XQPA-2PH2 — an MCP tool whose server-supplied `inputSchema` leaves the subset is rejected at the `Send` boundary with `ErrInvalidConfig` whose text attributes the failure as `<server>.<tool>`, and the whole `Send` fails rather than the single tool being dropped or degraded.
- R-U3C5-4A1V — a tool schema whose `format` value is outside the nine-value allowlist (e.g. `uri`, `uri-reference`, `regex`) is rejected at the `Send` gate with `ErrInvalidConfig` naming the format and its location; each of the nine allowlisted values passes.
- R-6QNT-WR7C — a tool schema whose `enum` contains a non-string value (e.g. `"enum": [1, 2]`) or whose `const` is a non-string value (e.g. `"const": 5`) is rejected at the `Send` gate with `ErrInvalidConfig` naming the construct and its location; string-valued `enum` and `const` pass.
- R-ZPPN-6FV9 — a tool schema whose root is not `"type": "object"` (e.g. a root `anyOf`, or a root `"type": "string"`) is rejected at the `Send` gate with `ErrInvalidConfig` naming the root shape, even when every construct it contains is individually inside the subset; a gate that validates only construct membership and not the root shape fails this.
